\begin{abstract}
	Checkpoint and time-travel features, increasingly adopted in LLM agent frameworks for recovery and exploration, reintroduce a classic systems challenge: externally visible outputs cannot be rolled back. For tool-using LLM agents, the gap is \emph{semantic}: after restore, an agent may re-synthesize a logically equivalent action with different parameters (e.g., a fresh idempotency key), silently bypassing at-most-once defenses and potentially reviving consumed credentials. We characterize two vulnerability classes---\emph{Action Replay} and \emph{Authority Resurrection}---and reproduce them in a proof-of-concept testbed with MCP tool servers and session-level restore. We then present \sys{} (Agent Checkpoint-Restore Fence), a \emph{fork-aware tool-effect journal} that persists effect receipts and enforces an explicit replay-vs-fork decision for irreversible tool calls. In our evaluation, \sys{} eliminates duplicate commits under restore while preserving the agent's ability to explore alternative plans via explicit forking.
\end{abstract}

\section{Background and Motivation}

\subsection{Checkpoint-Restore Mechanisms in Classical Systems}

\emph{Checkpoint-restore (CR)} saves and resumes process state~\cite{criu}, but cannot rewind external services. This creates the \textit{output commit problem}~\cite{elnozahy2002survey, strom1985optimistic}: outputs must be delayed, logged, or virtualized so that recovery does not duplicate irreversible effects. After restore, external state (payment processors, cloud APIs) reflects previously committed effects while the process believes it is ``before'' them, creating \emph{state divergence}.

\subsection{LLM Agents and Their Need for Checkpoint-Restore}

LLM agents manage cloud resources, payments, and software engineering tasks~\cite{sweagent, openhands}, making exploration and backtracking essential~\cite{xu2025agenticexploration}. Agent frameworks expose persistent checkpoints and time-travel as first-class features~\cite{langgraph, langgraph_durable}; durable execution guidance explicitly warns that resumed execution may rerun steps with side effects and recommends making them idempotent~\cite{langgraph_functional_idempotency}. Recent work on agentic exploration highlights external side effects as a core unresolved challenge, arguing that services must become fork-aware or calls must be intercepted~\cite{xu2025agenticexploration}. However, ``idempotent'' is a \emph{caller--service contract} that presumes stable operation identity across retries. LLM agents violate this: they re-synthesize semantically equivalent tool calls with different parameters after restore, even under nominally deterministic settings~\cite{atil2025nondeterminism, khatchadourian2026replayable}. Tool invocation is standardized via protocols such as MCP~\cite{mcp_spec}. Durable engines like Temporal record nondeterministic values for replay~\cite{temporal_side_effects}, but require deterministic workflow structure that LLM agents cannot provide.

\subsection{Related Work and Limitations of Existing Solutions}

\textbf{Durable workflows.} RPC at-most-once semantics~\cite{birrell1984rpc} are operationalized via idempotency keys: same key + same parameters $\to$ same effect; different parameters $\to$ conflict/rejection~\cite{stripe_idempotent_requests, aws_ecs_idempotency, ietf_idempotency_key}. Durable engines record non-deterministic values in event histories so replay reuses recorded results~\cite{temporal_side_effects}, but assume deterministic workflow structure.
\textbf{Agent replay and debugging.} Record-and-replay has been applied to agent frameworks to improve reliability and cost~\cite{feng2025agentrR}, and interactive debugging tools support resetting and forking conversations~\cite{ma2025dover}. Agent security mechanisms enforce privilege control and runtime policies~\cite{progent, agentspec, owaspllm}. None address how checkpoint-restore interacts with \emph{irreversible tool effects} to create a security attack surface.
\textbf{Snapshot-induced anomalies.} TEE rollback protection~\cite{parno2011memoir, matetic2017rote} assumes deterministic programs and a stronger adversary. In real systems, a Vault issue documents single-use tokens reappearing after snapshot restore~\cite{vault_issue_28378}, motivating stateful consumption tracking.

We propose \sys{} (Agent Checkpoint-Restore Fence), a runtime mechanism that enforces fork-aware tool-effect semantics to prevent semantic rollback attacks.

\section{Threat Model}

We target two invariants standard in durable, side-effecting systems: (1) no replay of irreversible effects (restore must not commit a payment or resource creation more than once for the same logical operation), and (2) revocation monotonicity (consumed credentials must not become usable again after restore). We consider two attacker models. In \emph{Time-Travel Abuse}, the platform exposes checkpoint-restore for exploration and backtracking~\cite{langgraph}, and an adversary (authenticated user or legitimate workflow) may trigger security violations, analogous to restart attacks in TEE literature~\cite{matetic2017rote}. In \emph{Fault-Triggered Restore}, crashes or OOM kills trigger restoration from a checkpoint, and the attacker only influences inputs and benefits from outcomes (duplicate payments).

\section{Attacks}

The root cause is \emph{state divergence}: checkpoint-restore rolls back the agent's internal state but external services retain theirs. Combined with LLM non-determinism, the agent re-synthesizes tool calls with different parameters after restore, causing external services to treat replayed requests as new operations. We identify two attack classes: \emph{Action Replay}, which exploits idempotency key instability after restore to enable duplicate commits (financial fraud, denial-of-wallet); and \emph{Authority Resurrection}, which exploits consumed single-use tokens that reappear in rolled-back agent state to enable unauthorized operations under stateless validation. Action Replay applies to both attacker models, while Authority Resurrection requires Time-Travel Abuse where the attacker controls post-restore prompts.

\subsection{Action Replay Attack}
\label{sec:v1}

Figure~\ref{fig:action-replay} illustrates this attack. If a checkpoint is taken before an external commit is durably recorded, restoring re-executes the same logical operation. Idempotency keys are a caller--service contract: same key + same parameters yields the stored result; changed parameters cause a conflict or rejection~\cite{stripe_idempotent_requests, aws_ecs_idempotency}. Semantic drift after restore violates this contract---the LLM regenerates a \emph{different} key for the \emph{same} logical operation, so the service treats it as a new request. The attack succeeds when two committed entries exist for the same logical operation, enabling duplicate payments, resource provisioning, or denial-of-wallet.

\subsection{Authority Resurrection Attack}
\label{sec:v2}

Agents hold credentials or single-use approvals in memory; restoring a checkpoint reintroduces consumed tokens, enabling reuse. Exploitability depends on the validation model: with stateless validation (signature check only), tokens are accepted if cryptographically valid; with stateful validation (revocation list), reuse is rejected. The attack succeeds when a consumed token is accepted after restore.

\section{Design: \sys}
\label{sec:design}

\sys{} interposes at the tool boundary (e.g., as an MCP proxy) and treats each \emph{irreversible} tool call as an \emph{effect} that must have a stable identity across restores. Rather than relying on the LLM to regenerate an identical idempotency key, \sys{} assigns each effect a stable \texttt{op\_slot} (a monotonic index within a run) and stores an \emph{effect receipt}:
$\langle \texttt{thread\_id}, \texttt{branch\_id}, \texttt{op\_slot}, \texttt{tool}, \texttt{fp(args)}, \texttt{req}, \texttt{resp} \rangle$
where \texttt{fp} is a deterministic normalization of tool arguments (canonical JSON).

\textbf{Replay vs.\ fork semantics.} Upon restore, if the agent issues an irreversible tool call at an \texttt{op\_slot} that already has a receipt, \sys{} compares fingerprints: (i)~if they match, \sys{} returns the recorded response without reissuing the side effect (\emph{replay}); (ii)~if they differ, \sys{} surfaces a \emph{conflict} and requires an explicit fork (new \texttt{branch\_id}) before allowing a new effect. This makes exploration explicit rather than silently duplicating effects---the key design choice that distinguishes \sys{} from naive deduplication.

\textbf{Credential monotonicity.} For single-use approvals, \sys{} records token consumption in effect receipts. Combined with stateful server-side validation (which rejects reused tokens~\cite{vault_issue_28378}), this prevents Authority Resurrection. We leave full branch management and automated fork policies to future work.

\section{Evaluation}

\subsection{Experimental Setup}

Our testbed uses Claude Code CLI backed by Qwen3-32B, with checkpoint-restore simulated via session file truncation. External services are MCP servers with append-only logs: a bank (\texttt{transfer} with UUID idempotency), cloud provider (\texttt{create\_server}), and approval service (configurable stateless/stateful validation). Checkpoints are placed after verification but before commit, the most vulnerable point. As baseline, we truncate sessions \textit{after} the action to confirm duplication requires checkpoint-restore timing.

\textbf{Limitations.} Our testbed simulates CR via session truncation rather than CRIU, sample sizes are limited, and we evaluate one model family (Qwen3-32B). The fork-conflict path (fingerprint mismatch) is validated manually rather than at scale.

\section{Discussion and Conclusion}

Checkpoint-restore in LLM agent frameworks reintroduces the output commit problem in a setting where traditional solutions---which assume deterministic replay---do not apply. Our experiments confirm that semantic drift after restore consistently produces duplicate commits and can revive consumed credentials. \sys{} addresses this by making tool-effect identity an explicit runtime semantic layer: each irreversible effect gets a stable slot, and restore triggers a replay-vs-fork decision rather than silent re-execution. The key insight is that \emph{not} all post-restore divergence is harmful---agents legitimately explore alternative plans---but irreversible effects must be gated by an explicit fork decision. We believe this fork-aware discipline complements existing durable-execution and idempotency guidance~\cite{temporal_side_effects, langgraph_durable} by addressing the semantic gap that LLM non-determinism creates.
