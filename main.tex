\title{Semantic Rollback Attacks on Checkpoint-Restore in LLM-Driven Agents}

\begin{abstract}
	Checkpoint-restore mechanisms, increasingly adopted in LLM agent frameworks for fault tolerance and exploration, reintroduce a classic distributed systems challenge: the output commit problem. Unlike deterministic workflows where logged outputs enable consistent replay, LLM agents produce non-deterministic yet semantically equivalent actions upon restoration, causing state divergence between rolled-back agent state and persistent external state. This semantic drift defeats traditional idempotency mechanisms. We identify two vulnerability classes: (1) Action Replay, where post-restore action synthesis generates different idempotency keys, bypassing duplicate detection and enabling financial fraud; and (2) Authority Resurrection, where consumed single-use tokens are unintentionally revived after restore. Our proof-of-concept experiments demonstrate that action duplication and token reuse consistently occur under common configurations. We present \sys{}, a runtime mechanism that maintains stable operation identities across restores, reducing duplicate commits to zero in our evaluation.
\end{abstract}

\section{Background and Motivation}

\subsection{Checkpoint-Restore Mechanisms in Classical Systems}

\emph{Checkpoint-restore (CR)} enables saving process state to disk and later resuming execution. Systems like CRIU~\cite{criu} can freeze Linux processes or containers, capturing memory, registers, file descriptors, and network connections. Upon restoration, the process resumes from the exact checkpoint, unaware that time has passed or external state may have changed. This creates a classic distributed systems challenge: the \textit{output commit problem}~\cite{elnozahy02survey, stromyemini85}. Classic rollback-recovery techniques address this through checkpointing and message logging. Foundational protocols require that externally visible outputs be delayed until stable or recorded to prevent duplicate effects~\cite{elnozahy2002survey, strom1985optimistic, alvisi1998messagelogging}. Traditional solutions assume piecewise-deterministic execution: systems like Manetho and ReViveI/O log or virtualize external effects to achieve fast output commit with bounded rollback~\cite{elnozahy1992manetho, reviveio2006}. Modern platforms have extended these mechanisms to container and orchestration environments. Kubernetes has been actively productizing container checkpointing, including KEP-2008 and the Kubelet Checkpoint API, enabling container checkpoint and restore for debugging, migration, and recovery~\cite{k8scheckpoint,k8s_kep2008,k8s_checkpoint_api}. A key limitation is that these mechanisms do \emph{not} snapshot external services that the process interacts with; after restore, the application resumes as if time has rewound, while external state (payment processors, cloud control planes, Git platforms) reflects previously committed effects.

\subsection{LLM Agents and Their Need for Checkpoint-Restore}

Large-language-model (LLM) agents are increasingly deployed in production settings, managing cloud resources, processing payments, and automating software engineering tasks~\cite{sweagent, openhands}, requiring fault tolerance and debugging capabilities. Agentic research treats backtracking as essential for agent reasoning and exploration~\cite{agenticexploration,xu2025agenticexploration}. Agent frameworks like LangGraph provide persistent checkpoints and time-travel interfaces as first-class features~\cite{langgraph, langgraph_durable,langgraph_persistence,langgraph_timetravel}, enabling durable execution and explicit time-travel APIs where resuming from a checkpoint yields a new \emph{fork}; documentation emphasizes that external API calls should be idempotent to avoid duplicate effects~\cite{langgraph_functional_idempotency}. However, LLM agents violate the determinism assumption required by traditional CR: their runtime synthesis produces non-deterministic yet semantically equivalent behaviors~\cite{llmnondeterminism} even with temperature=0~\cite{atil2025nondeterminism}, and audit replay requires explicit harnesses to enforce determinism~\cite{khatchadourian2026replayable}. Tool-use architectures (ReAct, Toolformer) interleave reasoning with structured actions~\cite{yao2022react,schick2023toolformer}, often standardized via MCP~\cite{mcp_spec,mcp_anthropic}. Modern durable execution engines like Temporal make the output-commit contract explicit: \texttt{SideEffect} mechanisms record nondeterministic values (e.g., UUIDs) so they are \emph{reused on replay} rather than recomputed~\cite{temporal,temporal_side_effects,temporal_activity_definition}, preventing ``UUID drift'' by moving identity generation into a durable log. LLM agents cannot provide the determinism guarantee these engines require, creating mismatches where restored agent state no longer aligns with irreversible external states such as committed payments or consumed credentials.

\subsection{Related Work and Limitations of Existing Solutions}

Building on the classical output commit and rollback-recovery foundations discussed above~\cite{elnozahy2002survey,strom1985optimistic,alvisi1998messagelogging,elnozahy1992manetho,reviveio2006}, RPC-based at-most-once semantics~\cite{birrellnelson84,birrell1984rpc} have been operationalized in modern API ecosystems via idempotency keys, with provider-specific contracts binding ``same key + same parameters'' to ``same effect''~\cite{stripe_idempotent_requests,aws_ecs_idempotency,ietf_idempotency_key}. These mechanisms assume that the caller preserves a \emph{stable operation identity} across retries; this assumption fails when keys are synthesized non-deterministically by LLM agents, silently violating the application-level idempotency contract. Durable workflow engines address this by capturing nondeterministic values into an event history for replay~\cite{temporal_side_effects,temporal_activity_definition}, but LLM agents cannot provide the required determinism guarantees. In TEEs, Memoir provides state continuity against correct-but-stale replay~\cite{parno2011memoir}, ROTE implements distributed rollback protection~\cite{matetic2017rote}, and fork-linearizability protocols detect rollback via consistent operation histories~\cite{brandenburger2017lcm}; these works assume a stronger adversary (untrusted OS/storage) but also deterministic programs and stable identifiers, whereas semantic rollback attacks arise from benign restores where the agent \emph{itself} re-synthesizes requests differently. AgentRR provides record-and-replay for LLM agents targeting reliability and cost~\cite{feng2025agentrR}; DoVer addresses intervention-driven debugging where branching traces complicate attribution~\cite{ma2025dover}; and agent-specific security mechanisms constrain permissible actions but do not address state continuity across checkpoint-restore~\cite{progent,agentspec,owaspllm,xu2025agenticexploration,mcp_spec,mcp_anthropic}. None of these characterize security failures from semantic drift across restore or propose a commit discipline for irreversible tool effects. A real-world Vault incident documents token reuse after snapshot restore~\cite{vault_issue_28378,vaultissue}, illustrating the practical need for stateful consumption tracking.

We present \sys{}, a runtime mechanism that maintains stable operation identities across restores to mitigate these vulnerabilities.

\section{Threat Model}

\subsection{Security Goals}

We focus on invariants that are standard in durable, side-effecting systems:

\begin{itemize}
	\item \textbf{No replay of irreversible effects}: Restoring or retrying should not commit a payment, ticket, or resource creation more than once for the same logical operation.

	\item \textbf{Revocation monotonicity}: Once credentials or approvals are revoked or consumed, restore must not make them usable again.
\end{itemize}

\subsection{Attacker Models}

We consider two attacker models. In \emph{Fault-Triggered Restore}, the agent is checkpointed for recovery; crashes or OOM kills trigger restoration. The attacker only influences inputs (emails, documents) and benefits from outcomes (duplicate payments); no special access is required. In \emph{Time-Travel Abuse}, the platform exposes time travel as a feature~\cite{langgraph}, and an adversary (authenticated user or legitimate workflow) may trigger security violations, analogous to restart attacks in TEE literature~\cite{rote}.

\subsection{Out of Scope}

We do not assume compromise of cryptographic primitives, the checkpoint mechanism itself, physical access to the execution environment, or modification of the agent's code or model weights.

\section{Attacks}

The root cause is \emph{state divergence}: checkpoint-restore rolls back the agent's internal state but external services retain theirs. Combined with LLM non-determinism, the agent re-synthesizes tool calls with different parameters after restore, causing external services to treat replayed requests as new operations. We identify two attack classes: \emph{Action Replay}, which exploits idempotency key instability after restore to enable duplicate commits (financial fraud, denial-of-wallet); and \emph{Authority Resurrection}, which exploits consumed single-use tokens that reappear in rolled-back agent state to enable unauthorized operations under stateless validation. Action Replay applies to both attacker models, while Authority Resurrection requires Time-Travel Abuse where the attacker controls post-restore prompts.

\subsection{Action Replay Attack}
\label{sec:v1}

Figure~\ref{fig:action-replay} illustrates this attack. If a checkpoint is taken before an external commit is durably recorded, restoring re-executes the same operation, enabling denial-of-wallet (crash after resource provisioning inflates victim's bill) and financial fraud (time-travel after receiving service to avoid payment). In classic durable execution, idempotency keys prevent duplicates~\cite{temporal, stripeidempotency}, but LLM agents regenerate different keys after restore, causing duplicate payments, tickets, resource provisioning, or PRs. The attack succeeds when two committed entries exist for the same logical operation.

\subsection{Authority Resurrection Attack}
\label{sec:v2}

Figure~\ref{fig:authority-resurrection} illustrates this attack. Agents hold credentials or single-use approvals in memory; restoring a checkpoint reintroduces consumed tokens, enabling reuse attacks. Exploitability depends on the validation model: with stateless validation (signature check only), tokens are accepted if cryptographically valid; with stateful validation (revocation list), reuse is rejected. The attack succeeds when a consumed token is accepted after restore.

\section{Evaluation}

\subsection{Experimental Setup}

We evaluate semantic rollback vulnerabilities through proof-of-concept experiments. Our testbed uses Claude Code CLI backed by Qwen3-32B, with checkpoint-restore simulated via session file truncation (mirroring application-level time-travel features like LangGraph). External services are MCP servers with append-only logs: a bank (\texttt{transfer} with UUID idempotency), cloud provider (\texttt{create\_server}), and approval service (configurable stateless/stateful validation). Checkpoints are placed after verification (e.g., \texttt{check\_balance}) but before commit (e.g., \texttt{transfer}), the most vulnerable point. We test four scenarios: bank transfer, cloud provisioning, approval-based deletion, and payment. As baseline, we truncate sessions \textit{after} the action to confirm duplication requires checkpoint-restore timing.

\subsection{Results}

For Action Replay, all 20 checkpoint-restore trials (10 transfer, 10 cloud) exhibited key instability and action duplication: the LLM regenerated different idempotency keys after restore, causing duplicate commits in every case; all 10 baseline trials showed 0\% duplication, confirming the vulnerability stems from checkpoint timing, not agent behavior. For Authority Resurrection, we tested token reuse under three validation modes (2 trials each): stateless (signature-only), stateful\_sync (immediate revocation check), and stateful\_async (delayed check). With stateless validation, consumed tokens were accepted for unauthorized targets in 2/2 approval trials (deleting Bob's data with Alice's token). Stateful validation (both sync and async) rejected reuse in all trials (0/2 vulnerable). Payment scenarios showed mixed results requiring larger sample sizes.

\subsection{Limitations}

Our testbed simulates checkpoint-restore via session truncation rather than OS-level mechanisms like CRIU; future work should validate with process-level checkpointing. Sample sizes are limited (10--20 trials for Action Replay, 2 for Authority Resurrection), and we evaluate only one model family (Qwen3-32B). Task prompts explicitly request UUID generation, potentially inflating key instability rates.

\section{Mitigation Strategies}

For Action Replay, agent frameworks should persist idempotency keys to durable storage before tool calls and reload them after restore, ensuring key stability across restores; external services should implement semantic-level deduplication based on operation identity rather than relying solely on caller-provided keys. For Authority Resurrection, services should use synchronous stateful token validation (checking consumption state in real-time) rather than stateless JWT-only validation, and issue short-lived tokens to minimize the attack window. At the framework level, agent systems should define explicit checkpoint-safe boundaries ensuring external commits are recorded in agent state before checkpointing, and provide restore hooks that re-validate credentials and check for already-committed actions upon restore.

\section{Conclusion}

Checkpoint-restore primitives are becoming standard in LLM agent frameworks, yet their integration reintroduces the output commit problem in a setting where traditional solutions fail: LLM non-determinism defeats idempotency mechanisms, and agent state rollback does not affect external systems. Our proof-of-concept experiments demonstrate that action replay and authority resurrection consistently occur under common configurations. \sys{} addresses these vulnerabilities by maintaining stable operation identities across restores, reducing duplicate commits to zero in our evaluation. More broadly, securing checkpoint-restore for non-deterministic agents requires a commit discipline that preserves logical operation identity across state divergence.
