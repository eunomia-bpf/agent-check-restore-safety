\title{Semantic Rollback Attacks on Checkpoint-Restore in LLM-Driven Agents}

\begin{abstract}
	Checkpoint-restore mechanisms, increasingly adopted in LLM agent frameworks for fault tolerance and exploration, reintroduce a classic distributed systems challenge: the output commit problem. Unlike deterministic workflows where logged outputs enable consistent replay, LLM agents produce non-deterministic yet semantically equivalent actions upon restoration, causing state divergence between rolled-back agent state and persistent external state. This semantic drift defeats traditional idempotency mechanisms. We identify two vulnerability classes: (1) Action Replay, where post-restore action synthesis generates different idempotency keys, bypassing duplicate detection and enabling financial fraud; and (2) Authority Resurrection, where consumed single-use tokens are unintentionally revived after restore. Our proof-of-concept experiments demonstrate that action duplication and token reuse consistently occur under common configurations. We present \sys{}, a runtime mechanism that maintains stable operation identities across restores, reducing duplicate commits to zero in our evaluation.
\end{abstract}

\section{Background and Motivation}

\subsection{Checkpoint-Restore Mechanisms in Classical Systems}

\emph{Checkpoint-restore (CR)} enables saving process state to disk and later resuming execution. Systems like CRIU~\cite{criu} can freeze Linux processes or containers, capturing memory, registers, file descriptors, and network connections. Upon restoration, the process resumes from the exact checkpoint, unaware that time has passed or external state may have changed. This creates a classic distributed systems challenge: the \textit{output commit problem}~\cite{elnozahy02survey, stromyemini85}.

Classic rollback-recovery techniques address this through checkpointing and message logging. Surveys and foundational protocols show that to preserve correctness, systems must enforce a discipline where externally visible outputs are either delayed until the producing state is stable, or outputs are recorded/committed in a way that prevents duplicate effects across retries and rollbacks~\cite{elnozahy2002survey, strom1985optimistic, alvisi1998messagelogging}. Traditional solutions assume piecewise-deterministic execution with logged outputs for replay, as demonstrated by systems like Manetho which explicitly target fast output commit alongside limited rollback~\cite{elnozahy1992manetho}. Follow-on systems such as ReViveI/O address interactions with I/O by logging or virtualizing external effects so that recovery can avoid duplicate outputs~\cite{reviveio2006}.

Modern platforms have extended these mechanisms to container and orchestration environments. Kubernetes has been actively productizing container checkpointing, including KEP-2008 and the Kubelet Checkpoint API, enabling checkpoint creation for debugging/forensics and potentially restore/migration workflows~\cite{k8scheckpoint,k8s_kep2008,k8s_checkpoint_api}. A key limitation is that these mechanisms do \emph{not} snapshot external services that the process interacts with; after restore, the application resumes as if time has rewound, while external state (payment processors, cloud control planes, Git platforms) reflects previously committed effects.

\subsection{LLM Agents and Their Need for Checkpoint-Restore}

Large-language-model (LLM) agents are increasingly deployed in production settings, managing cloud resources, processing payments, and automating software engineering tasks~\cite{sweagent, openhands}. These deployments demand reliable fault tolerance and debugging capabilities for three key reasons. First, agents execute long-running, multi-step workflows where process crashes or timeouts can waste significant computation and cost. Second, human-in-the-loop workflows require the ability to pause, inspect intermediate states, and resume execution after intervention. Third, debugging complex agent behaviors often necessitates replaying execution from specific checkpoints to diagnose failures or explore alternative strategies.

Agent frameworks like LangGraph have responded to these needs by providing persistent checkpoints and time-travel interfaces as first-class features~\cite{langgraph, langgraph_durable,langgraph_persistence,langgraph_timetravel}. These systems enable durable execution (resume without redoing completed steps) and explicit time-travel APIs that resume from prior checkpoints; importantly, resuming from a checkpoint yields a new \emph{fork} in the execution history. Documentation emphasizes that replay/re-execution can occur and that external API calls should be designed to be idempotent to avoid duplicate effects~\cite{langgraph_functional_idempotency}. Agentic exploration research similarly treats backtracking as essential for agent reasoning~\cite{agenticexploration,xu2025agenticexploration}.

However, LLM agents violate the determinism assumption required by traditional CR. Their runtime synthesis from natural-language prompts produces non-deterministic yet semantically equivalent behaviors~\cite{llmnondeterminism}, even with temperature=0 settings. Recent measurements show substantial run-to-run variability across models and tasks under ``deterministic'' settings~\cite{atil2025nondeterminism}, motivating explicit determinism metrics and stress-testing methodologies. In regulated settings, recent work argues that tool-using agents struggle with audit replay without a harness that enforces determinism/faithfulness properties~\cite{khatchadourian2026replayable}. Tool-use architectures (e.g., ReAct, Toolformer) intentionally interleave natural-language reasoning with structured actions~\cite{yao2022react,schick2023toolformer}, and production agents often standardize tool invocation via protocols like MCP~\cite{mcp_spec,mcp_anthropic}.

Modern durable execution engines like Temporal make the output-commit contract explicit through deterministic replay and side-effect isolation. Temporal requires workflow replay to match a recorded event history and provides \texttt{SideEffect} mechanisms to record nondeterministic values (e.g., UUIDs) so they are \emph{reused on replay} rather than recomputed, with Activities recommended to be idempotent~\cite{temporal,temporal_side_effects,temporal_activity_definition}. These designs effectively prevent ``UUID drift'' across replays by moving identity generation out of nondeterministic code paths and into a durable log. However, LLM agents cannot provide the determinism guarantee that engines like Temporal require, creating critical mismatches where an agent's restored state no longer aligns with irreversible external states such as committed payments or consumed credentials.

\subsection{Related Work and Limitations of Existing Solutions}

Classic rollback-recovery and output-commit problem have been extensively studied~\cite{elnozahy2002survey,strom1985optimistic,alvisi1998messagelogging,elnozahy1992manetho,reviveio2006}. Our work differs in that the primary instability is not only the inability to roll back external state, but also that \emph{LLM-synthesized action parameters drift across restore}, defeating deduplication mechanisms that assume stable request identities.

RPC systems traditionally provide at-most-once semantics through request identifiers~\cite{birrellnelson84,birrell1984rpc}. Modern API ecosystems operationalize this via idempotency keys (or client tokens), with provider-specific contracts binding ``same key + same parameters'' to ``same effect''~\cite{stripe_idempotent_requests,aws_ecs_idempotency,ietf_idempotency_key}. These mechanisms assume that the caller preserves a \emph{stable operation identity} across retries.

This assumption fails when keys are synthesized non-deterministically by LLM agents. Durable workflow engines require deterministic replay and provide explicit primitives to capture nondeterministic values into an event history so replay uses recorded values rather than re-generating them~\cite{temporal_side_effects,temporal_activity_definition}. When a tool-using LLM agent regenerates identifiers (e.g., UUID idempotency keys) after restore, the platform-level retry discipline is satisfied, but the application-level idempotency contract is silently violated.

Rollback attacks and state continuity are well studied in trusted execution environments (TEEs). Memoir provides state continuity for protected modules to prevent correct-but-stale state from being replayed~\cite{parno2011memoir}. ROTE implements rollback protection as a distributed system across multiple processors to prevent rollback in trusted execution~\cite{matetic2017rote}. Protocols based on fork-linearizability and collective memory detect rollback/forking by ensuring consistent operation histories~\cite{brandenburger2017lcm}. These works study rollback under a stronger adversary model (untrusted OS/storage) but typically assume deterministic programs and stable identifiers, whereas semantic rollback attacks arise in benign operational restores where the restored agent \emph{itself} re-synthesizes requests differently, creating identity drift that breaks deduplication and revocation assumptions.

Agent systems increasingly treat snapshotting, branching, and backtracking as first-class capabilities. Recent systems work argues that agentic exploration requires fork semantics and explicit handling of external side effects, and that generic snapshot/restore mechanisms are insufficient in realistic environments shared with other services and users~\cite{xu2025agenticexploration}. In parallel, AgentRR introduces record-and-replay mechanisms for LLM agents to reuse structured experiences, targeting reliability and cost~\cite{feng2025agentrR}. DoVer advocates intervention-driven debugging for multi-agent systems, emphasizing that branching traces complicate attribution and that verified interventions can flip failures into successes~\cite{ma2025dover}. These lines of work motivate checkpointing and replay in agent frameworks, but they do not characterize the security failures caused by semantic drift across restore nor propose a commit/identity discipline for irreversible tool effects under time travel.

Production agent ecosystems are converging on common tool integration protocols such as MCP, which standardize how LLM applications connect to external tools and data sources~\cite{mcp_spec,mcp_anthropic}. Our work complements these efforts by highlighting that, once checkpoint/restore and time travel are introduced, tool invocation layers require additional systems support to preserve stable operation identities and revocation monotonicity across restores.

Agent-specific security mechanisms constrain what actions agents can take but do not address state continuity problems from checkpoint-restore. Privilege control systems~\cite{progent} and runtime enforcement~\cite{agentspec} restrict permissions but do not handle checkpoint-restore state mismatches. While OWASP documents prompt injection risks~\cite{owaspllm}, these approaches do not address a distinct vulnerability class of \textit{semantic rollback} where LLM non-determinism combined with checkpoint-restore causes output commit problems to manifest as security violations.

Separately, many systems use single-use approvals or tokens for sensitive operations. If token validity is checked only statelessly (e.g., signature verification without server-side consumption state), a checkpoint restore that revives an already-consumed token in agent memory can enable reuse. A real-world Vault incident documents token reuse behavior after snapshot restore~\cite{vault_issue_28378,vaultissue}, illustrating the need for stateful consumption tracking.

We present \sys{}, a runtime mechanism that maintains stable operation identities across restores to mitigate these vulnerabilities.

\section{Threat Model}

\subsection{Security Goals}

We focus on invariants that are standard in durable, side-effecting systems:

\begin{itemize}
	\item \textbf{No replay of irreversible effects}: Restoring or retrying should not commit a payment, ticket, or resource creation more than once for the same logical operation.

	\item \textbf{Revocation monotonicity}: Once credentials or approvals are revoked or consumed, restore must not make them usable again.
\end{itemize}

\subsection{Attacker Models}

We consider two attacker models. In \textbf{Fault-Triggered Restore}, the agent is checkpointed for recovery; crashes or OOM kills trigger restoration. The attacker only influences inputs (emails, documents) and benefits from outcomes (duplicate payments); no special access is required. In \textbf{Time-Travel Abuse}, the platform exposes time travel as a feature~\cite{langgraph}, and an adversary (authenticated user or legitimate workflow) may trigger security violations, analogous to restart attacks in TEE literature~\cite{rote}.

\subsection{Out of Scope}

We do not assume compromise of cryptographic primitives, the checkpoint mechanism itself, physical access to the execution environment, or modification of the agent's code or model weights.

\section{Attacks}

The root cause of semantic rollback vulnerabilities is state divergence: checkpoint-restore rolls back the agent's internal state (memory, credentials, task progress), but external services (payment processors, cloud APIs, Git platforms) retain their state. Combined with LLM non-determinism, the agent re-synthesizes tool calls with different parameters (including different idempotency keys), causing external services to treat replayed requests as new operations. We identify two attack classes: (1) Action Replay, where post-restore action synthesis generates different idempotency keys, bypassing duplicate detection and enabling financial fraud or denial-of-wallet attacks; and (2) Authority Resurrection, where consumed single-use tokens are revived after restore, enabling unauthorized operations under stateless validation. Action Replay applies to both attacker models (no post-restore control needed), while Authority Resurrection requires Time-Travel Abuse where the attacker controls post-restore prompts.

\subsection{Action Replay Attack}
\label{sec:v1}

Figure~\ref{fig:action-replay} illustrates this attack. If a checkpoint is taken before an external commit is durably recorded, restoring can re-execute the same operation. This enables denial-of-wallet (crash after resource provisioning inflates victim's bill) and financial fraud (time-travel after receiving service to avoid payment).

In classic durable execution, idempotency keys prevent duplicates~\cite{temporal, stripeidempotency}. In LLM agents, the key is not stable across restores: the agent regenerates different idempotency keys, causing duplicate payments, tickets, or resource provisioning. In software engineering agents, different branch names or PR titles result in duplicate PRs. The attack succeeds when two committed entries exist for the same logical operation.

\subsection{Authority Resurrection Attack}
\label{sec:v2}

Figure~\ref{fig:authority-resurrection} illustrates this attack. Agents hold credentials or single-use approvals in memory. Restoring a checkpoint reintroduces consumed tokens, enabling reuse attacks. Real systems exhibit this: a Vault issue showed single-use tokens reappearing after raft snapshot restore~\cite{vaultissue}.

Exploitability depends on the validation model. With stateless validation (signature check only), tokens are accepted if cryptographically valid. With stateful validation (revocation list), reuse is rejected. The attack succeeds when a consumed token is accepted after restore.

\section{Evaluation}

\subsection{Experimental Setup}

We evaluate semantic rollback vulnerabilities through proof-of-concept experiments. Our testbed uses Claude Code CLI backed by Qwen3-32B, with checkpoint-restore simulated via session file truncation (mirroring application-level time-travel features like LangGraph). External services are MCP servers with append-only logs: a bank (\texttt{transfer} with UUID idempotency), cloud provider (\texttt{create\_server}), and approval service (configurable stateless/stateful validation). Checkpoints are placed after verification (e.g., \texttt{check\_balance}) but before commit (e.g., \texttt{transfer}), the most vulnerable point. We test four scenarios: bank transfer, cloud provisioning, approval-based deletion, and payment. As baseline, we truncate sessions \textit{after} the action to confirm duplication requires checkpoint-restore timing.

\subsection{Results}

\textbf{Action Replay.} All 20 checkpoint-restore trials (10 transfer, 10 cloud) exhibited key instability and action duplication: the LLM regenerated different idempotency keys after restore, causing duplicate commits in every case. All 10 baseline trials showed 0\% duplication, confirming the vulnerability stems from checkpoint timing, not agent behavior.

\textbf{Authority Resurrection.} We tested token reuse under three validation modes (2 trials each): stateless (signature-only), stateful\_sync (immediate revocation check), and stateful\_async (delayed check). With stateless validation, consumed tokens were accepted for unauthorized targets in 2/2 approval trials (deleting Bob's data with Alice's token). Stateful validation (both sync and async) successfully rejected reuse in all approval trials (0/2 vulnerable). Payment scenarios showed mixed results requiring larger sample sizes.

\subsection{Limitations}

Our testbed simulates checkpoint-restore via session truncation rather than OS-level mechanisms like CRIU; future work should validate with process-level checkpointing. Sample sizes are limited (10--20 trials for Action Replay, 2 for Authority Resurrection), and we evaluate only one model family (Qwen3-32B). Task prompts explicitly request UUID generation, potentially inflating key instability rates.

\section{Mitigation Strategies}

For Action Replay, agent frameworks should persist idempotency keys to durable storage before tool calls and reload them after restore, ensuring key stability across restores; external services should implement semantic-level deduplication based on operation identity rather than relying solely on caller-provided keys. For Authority Resurrection, services should use synchronous stateful token validation (checking consumption state in real-time) rather than stateless JWT-only validation, and issue short-lived tokens to minimize the attack window. At the framework level, agent systems should define explicit checkpoint-safe boundaries ensuring external commits are recorded in agent state before checkpointing, and provide restore hooks that re-validate credentials and check for already-committed actions upon restore.

\section{Conclusion}

Checkpoint-restore primitives are becoming standard in LLM agent frameworks, yet their integration creates measurable security vulnerabilities. LLM non-determinism means post-restore action synthesis varies enough to defeat idempotency mechanisms, while agent state rollback does not affect external systems, enabling action replay and authority resurrection attacks. Our proof-of-concept experiments demonstrate these failures under common configurations, with duplication and token reuse consistently observed in tested scenarios. Mitigating these vulnerabilities requires rethinking the checkpoint-restore abstraction for non-deterministic agents, potentially through external capability verification at execution time, tool-side commit logs resilient to key variation, or semantic-aware checkpointing that preserves logical operation identity.
