\begin{abstract}
Checkpoint and restore mechanisms are critical primitives used broadly for fault tolerance, incremental exploration, and debugging of software systems. Their integration into large-language-model (LLM)-driven agents---autonomous systems dynamically synthesizing execution plans and security-critical decisions from natural-language prompts---has received limited attention despite growing deployment. Recent systems work argues that agentic exploration fundamentally needs fast branching, backtracking, and snapshot/restore support~\cite{agenticexploration}, while production agent frameworks already expose persistent checkpoints and time travel to resume or fork past executions~\cite{langgraph}. We show that na\"ively applying traditional snapshot and restore primitives to LLM-based agents introduces a novel and severe class of security vulnerabilities we term \textbf{semantic rollback attacks}. Unlike traditional workflows with deterministic replay semantics, LLM agents inherently produce non-deterministic yet semantically equivalent actions upon restoration, causing mismatches between internal agent state and external irreversible system states.

In this paper, we systematically define, characterize, and experimentally demonstrate three key semantic rollback vulnerabilities: (1) \textbf{Authority Resurrection}, wherein revoked or expired credentials are unintentionally revived upon restoration; (2) \textbf{Action Duplication due to Identity Instability}, where semantically identical but structurally divergent restored requests bypass idempotency protections, causing repeated external side-effects such as payments or resource provisioning; and (3) \textbf{Security-Context Rollback}, in which previously committed security decisions and approvals are silently reverted.

To rigorously demonstrate and measure these vulnerabilities, we present \textbf{AgentRollback}, a reproducible evaluation toolkit designed to concretely simulate semantic rollback scenarios using CRIU checkpoint/restore~\cite{criu} plus external tool services with append-only logs. Our experiments using realistic agent tasks confirm the practical severity of these vulnerabilities, showing frequent duplication of external irreversible actions and authorization violations even under benign restoration scenarios. These findings reveal a critical semantic gap in current snapshot/restore integrations for LLM agents, and we advocate for fundamentally revisiting their secure integration within dynamic agent architectures.
\end{abstract}

\section{Introduction}

Large-language-model (LLM)-driven agents are increasingly deployed in software systems, enabling autonomous execution of complex tasks through dynamic synthesis of plans, security-critical decisions, and tool invocations from natural-language interactions. These agents now operate in production settings---managing cloud resources, processing payments, and automating customer interactions---which requires reliable fault tolerance, debugging, and crash recovery capabilities. Consequently, checkpoint and restore primitives, such as container checkpointing (CRIU~\cite{criu}) and VM snapshots, have become increasingly indispensable in supporting LLM agent reliability and debuggability.

Checkpoint/restore becomes operationally attractive for three reasons: (i) fault tolerance (restart after crashes/timeouts), (ii) debugging/time-travel (reproduce and inspect executions), and (iii) exploration (fork, backtrack, and search over alternative trajectories). Agentic exploration papers already treat snapshot/restore as a systems foundation and explicitly call out branching/backtracking as first-class needs~\cite{agenticexploration}. Practical frameworks now provide persistent checkpoints and explicit time-travel/forking interfaces for agent graphs~\cite{langgraph}.

However, traditional snapshot and restore mechanisms rely on deterministic replay semantics, where restarting from a checkpoint results in predictable and identical outcomes. Durable execution engines emphasize these assumptions explicitly: workflow code must be deterministic and external activities should be idempotent to tolerate retries without unexpected side effects~\cite{temporal}. This assumption is fundamentally violated by LLM agents, whose dynamic runtime synthesis from mutable natural-language prompts and untrusted external inputs inherently leads to non-deterministic yet semantically equivalent behaviors. When conventional snapshot/restore primitives are applied directly to these non-deterministic agents without considering their unique semantic properties, critical mismatches arise: an agent's internal restored state no longer aligns with irreversible external states (e.g., external payments already committed, credentials revoked, security decisions logged).

The root cause is a semantic mismatch: the external world does not roll back, while the agent's internal state (including credentials, approvals, and safety decisions expressed in prompts/memory) can be rewound and cloned; additionally, tool requests may be re-synthesized non-deterministically after restore, undermining standard idempotency assumptions. Payment and cloud APIs widely recommend idempotency keys so that retries do not create duplicate effects~\cite{stripeidempotency, awsidempotency}. These mechanisms assume the caller can reliably reuse a stable idempotency key across retries---an assumption that can fail if the key is produced implicitly by non-deterministic action synthesis.

The security community has studied rollback and forking in other settings---e.g., trusted execution environments---under a similar high-level principle: an attacker can violate ``state continuity'' by replaying old state or cloning instances, without breaking cryptography~\cite{memoir}. Our observation is that checkpoint/restore brings analogous risks to the application layer for tool-using agents, but with an important twist: LLM agents often reconstruct actions and policy decisions from natural language at runtime, making it harder to rely on stable step identities or deterministic replay.

This paper introduces the concept of \textbf{semantic rollback attacks} to precisely characterize these mismatches and vulnerabilities unique to LLM-driven agents. We identify three primary categories of semantic rollback vulnerabilities:

\begin{itemize}
    \item \textbf{Authority Resurrection}: Restored snapshots inadvertently revive previously revoked or expired credentials, thereby subverting authorization mechanisms.
    \item \textbf{Action Duplication due to Identity Instability}: Non-deterministic tool invocation parameters cause structurally distinct but semantically identical requests upon restoration, bypassing traditional idempotency checks and leading to repeated execution of external irreversible actions.
    \item \textbf{Security-Context Rollback}: Restoring conversational or internal agent states unintentionally reverts previously enforced security decisions, breaking critical compliance, integrity, and auditability constraints.
\end{itemize}

Although snapshot and restore have long been studied within the systems community, their integration into LLM-driven agents---and the resulting security implications---remains unexplored.

To systematically evaluate and quantify semantic rollback vulnerabilities, we present \textbf{AgentRollback}, a reproducible experimental framework designed explicitly to measure and demonstrate these attacks. Using realistic agent scenarios involving email notifications, payment processing, and resource provisioning, our experiments confirm the feasibility, realism, and severity of semantic rollback attacks, showing that standard snapshot-based techniques produce frequent duplicated external actions and unintended authorization reinstatements.

Our findings emphasize the fundamental semantic gap between conventional checkpoint/restore mechanisms and the intrinsic non-deterministic synthesis of LLM agents. Rather than simply reusing traditional mechanisms, we advocate designing snapshot/restore primitives with semantic awareness and robust security boundaries. We outline design principles toward achieving secure semantic compilation boundaries, separating dynamic agent synthesis from externally committed states.

In summary, we contribute:

\begin{enumerate}
    \item Formal identification and characterization of a novel category of security vulnerabilities---semantic rollback attacks---in snapshot-based LLM-driven agents.
    \item AgentRollback, a reproducible evaluation toolkit concretely demonstrating and quantifying these vulnerabilities through rigorous experimentation.
    \item A clear roadmap of critical design considerations and future research directions for securely integrating checkpoint/restore primitives into dynamic LLM agent architectures.
\end{enumerate}

This paper identifies the security implications of snapshot mechanisms for LLM agent deployments and outlines a research agenda for the systems and security communities.

\section{Background and Security Goals}

\subsection{Checkpoint/Restore Mechanisms}

CRIU (Checkpoint/Restore In Userspace) can freeze a Linux process or container, dump its state to disk, and later restore it to run ``as it was during the time of the freeze,'' enabling snapshots and debugging~\cite{criu}. However, this capability introduces risks when the process interacts with external systems that are not snapshotted.

Process-level checkpointing captures the complete execution state: memory contents, register values, file descriptors, and network connections. Upon restoration, the process resumes execution from the exact point where it was frozen, unaware that any time has passed or that external state may have changed.

\subsection{Time-Travel in Agent Frameworks}

Modern agent frameworks have embraced checkpoint/restore as a first-class feature. LangGraph persists checkpoints of a graph's state and exposes ``time travel'' to resume execution from a prior checkpoint and create a new fork in history~\cite{langgraph}. This makes restore/fork an explicit user-facing operation, not just a crash-recovery mechanism.

Time-travel debugging allows developers to:
\begin{itemize}
    \item Reproduce failed executions by restoring from checkpoints
    \item Explore alternative execution paths by forking from past states
    \item Iteratively refine agent behavior through trial-and-error exploration
\end{itemize}

These capabilities improve developer workflows but introduce the security concerns we analyze in this paper.

\subsection{Idempotency for External Side Effects}

Payment and cloud APIs widely recommend idempotency keys/client tokens so that retries do not create duplicate effects. Stripe documents idempotent requests and explains that the same idempotency key returns the same result for subsequent retries~\cite{stripeidempotency}. AWS EC2 documents that a RunInstances request with the same client token ``can complete only once'' within a scope, precisely to make retries safe~\cite{awsidempotency}.

These mechanisms assume the caller can reliably reuse a stable idempotency key across retries---an assumption that can fail if the key is produced implicitly by non-deterministic action synthesis in LLM agents.

\subsection{Security Goals and Invariants}

We focus on invariants that are standard in durable, side-effecting systems:

\begin{itemize}
    \item \textbf{No replay of irreversible effects}: Restoring/retrying should not commit a payment, ticket, or resource creation more than once for the same logical operation.

    \item \textbf{Revocation monotonicity}: Once credentials/approval are revoked or consumed, restore/fork must not make them usable again.

    \item \textbf{No authority amplification by forking}: Branching from a checkpoint should not allow multiple concurrent copies to exceed quotas or bypass single-instance constraints.

    \item \textbf{Instruction/data separation at the tool boundary}: Untrusted content should not become executable tool commands. OWASP lists prompt injection and insecure output handling among top risks for LLM applications~\cite{owaspllm}.
\end{itemize}

\section{Threat Model}

We consider two operationally realistic settings that capture how checkpoint/restore vulnerabilities can manifest in practice:

\subsection{TM1: Fault-Triggered Restore}

The agent is checkpointed for recovery; crashes, timeouts, or OOM kills cause the system or operator to restore from a prior checkpoint. In this threat model:

\begin{itemize}
    \item The attacker need not have ``restore privileges''
    \item The attacker may only influence inputs (emails, documents, web content)
    \item The attacker benefits from externally visible outcomes (duplicate payments, unauthorized actions)
    \item Restoration is triggered by legitimate system failures, not malicious action
\end{itemize}

This threat model requires no special access: normal operational failures combined with attacker-controlled inputs can trigger security violations.

\subsection{TM2: User-Visible Time Travel and Branch Exploration}

The platform or framework exposes time travel or forking as a feature (e.g., to resume from a checkpoint and explore alternatives)~\cite{langgraph}. In this setting:

\begin{itemize}
    \item An adversary may be an authenticated user abusing the time-travel feature
    \item A compromised orchestrator may start multiple instances from the same checkpoint
    \item Legitimate exploration workflows may inadvertently trigger security violations
\end{itemize}

This is analogous to restart/cloning capabilities modeled in rollback/forking literature for trusted execution environments~\cite{rote}.

\subsection{Out of Scope}

We do \textbf{not} assume:
\begin{itemize}
    \item Compromise of cryptographic primitives
    \item Compromise of the checkpoint mechanism itself
    \item Physical access to the execution environment
    \item Modification of the agent's code or model weights
\end{itemize}

\section{Vulnerability Scenarios}

We now detail three concrete vulnerability scenarios that arise from checkpoint/restore in LLM agents. Each scenario includes the attack mechanism, impact, and measurable success conditions.

\subsection{Replay of Irreversible Tool Actions}

If a checkpoint is taken before an external commit is durably recorded (or before the agent records that it has committed), restoring the checkpoint can re-execute the same logical operation.

\subsubsection{Attack Mechanism}

\begin{enumerate}
    \item Agent receives a task requiring an external action (e.g., ``process payment for order \#12345'')
    \item Checkpoint is taken at time $t_0$
    \item Agent synthesizes a tool call with parameters including an idempotency key $k_1$
    \item External service commits the action
    \item System crash occurs before agent records completion
    \item Agent is restored from checkpoint at $t_0$
    \item Agent re-synthesizes the tool call, but due to LLM non-determinism, generates a different idempotency key $k_2$
    \item External service treats this as a new request and commits again
\end{enumerate}

In classic durable execution, idempotency keys prevent duplicate effects~\cite{temporal, stripeidempotency}. In LLM agents, the failure mode is that the request identity may not be stable across restores: the agent may regenerate tool parameters or idempotency keys differently after restore, causing the external service to treat it as a new request.

\subsubsection{Impact}

\begin{itemize}
    \item Duplicate payments charged to users
    \item Duplicate tickets/issues created in tracking systems
    \item Duplicate resource provisioning (VMs, containers, storage)
    \item Duplicate emails or notifications sent
\end{itemize}

\subsubsection{Success Condition}

Two committed ledger entries exist for the same logical identifier (e.g., order\_id, ticket\_key, resource\_name) at the tool service.

\subsection{Revocation/Consumption Bypass via State Rewind}

Agents often hold credentials or ``one-time approvals'' in memory or local state. Restoring a checkpoint can reintroduce authorization material that was deleted or consumed after the checkpoint.

\subsubsection{Attack Mechanism}

\begin{enumerate}
    \item Agent receives a single-use authorization token $T$ at time $t_0$
    \item Checkpoint is taken
    \item Agent uses token $T$ for an authorized action
    \item Token $T$ is marked as consumed in the external authorization service
    \item Later, agent is restored from checkpoint (containing unexpired copy of $T$)
    \item Agent attempts to use $T$ again
\end{enumerate}

Real systems using snapshots can exhibit ``reappearing'' authorization objects after restore. A reported Vault issue demonstrates that a single-use token can reappear after raft snapshot restore, albeit in a stuck state~\cite{vaultissue}.

The vulnerability's exploitability depends on the external validation model:
\begin{itemize}
    \item \textbf{Stateless validation}: Token is accepted if cryptographically valid and not expired by timestamp
    \item \textbf{Stateful validation}: Token is checked against a revocation list or consumption database
    \item \textbf{Timing windows}: Even stateful systems may have propagation delays where revocation hasn't reached all validators
\end{itemize}

\subsubsection{Impact}

\begin{itemize}
    \item Bypassing intended revocation of credentials
    \item Reusing single-use authorization tokens
    \item Circumventing rate limits tied to credential consumption
    \item Violating audit trails that assume monotonic credential lifecycle
\end{itemize}

\subsubsection{Success Condition}

An authorization token that should be invalid (revoked/consumed) is accepted by the tool service after restore.

\subsection{Fork-Based Authority Amplification}

Time-travel/forking can create multiple concurrent agent copies from the same checkpoint. Even if each copy is ``correct,'' concurrency can violate quotas, rate limits, and single-instance assumptions.

\subsubsection{Attack Mechanism}

\begin{enumerate}
    \item Agent with budget/quota $Q$ is checkpointed at time $t_0$
    \item $N$ concurrent instances are restored from the same checkpoint
    \item Each instance believes it has access to budget $Q$
    \item Instances collectively consume $N \times Q$ resources before any coordination occurs
\end{enumerate}

This mirrors the well-studied ``forking'' dimension of rollback attacks in TEEs, where multiple instances are run concurrently from related states~\cite{rote}.

\subsubsection{Impact}

\begin{itemize}
    \item Denial-of-wallet attacks (cost amplification beyond intended budgets)
    \item Quota bypass (exceeding rate limits per principal)
    \item Confusing audit logs (multiple instances acting ``as the same agent'')
    \item Resource exhaustion in shared systems
\end{itemize}

\subsubsection{Success Condition}

The number of committed external actions exceeds the allowed bound for a principal in a time window (e.g., ``only one resource creation per user per minute'').

\section{Testbed Design and Evaluation Plan}

We propose a minimal testbed that isolates the semantic mismatch between checkpoint/restore and external state, enabling reproducible measurement of the vulnerabilities described above.

\subsection{Architecture}

\subsubsection{Agent Under Test (Inside Checkpoint Domain)}

Run the agent in a Linux container/namespace subject to CRIU checkpoint/restore~\cite{criu}. The agent:
\begin{itemize}
    \item Executes LLM-based planning and tool synthesis
    \item Maintains internal state (conversation history, credentials, task progress)
    \item Makes HTTP requests to external tool services
\end{itemize}

\subsubsection{Tool Services (Outside Checkpoint Domain)}

Run external ``tool'' services as separate processes/containers that are \textit{not} checkpointed. Each service maintains:
\begin{itemize}
    \item Append-only log of all received requests
    \item Durable state (committed transactions, consumed tokens)
    \item Idempotency enforcement based on client-provided keys
\end{itemize}

\subsubsection{Orchestrator}

A driver that:
\begin{itemize}
    \item Triggers checkpoints at controlled program points
    \item Kills/restores the agent at specified fault injection points
    \item Optionally forks $N$ copies from one checkpoint (for TM2 scenarios)
    \item Collects metrics from tool services
\end{itemize}

\subsection{Representative Workloads}

We define three workloads that represent common agent tasks with external side effects:

\begin{enumerate}
    \item \textbf{Payment-like tool}: \texttt{CreateCharge(order\_id, amount, idempotency\_key)}
    \begin{itemize}
        \item Service enforces idempotency by key
        \item Logs all requests with timestamps
        \item Returns success/duplicate/error status
    \end{itemize}

    \item \textbf{Ticket/email-like tool}: \texttt{CreateTicket(ticket\_key, fields...)}
    \begin{itemize}
        \item Service commits a ticket record
        \item Deduplication based on ticket\_key if provided
        \item Simulates notification side effects
    \end{itemize}

    \item \textbf{Provisioning-like tool}: \texttt{CreateVM(resource\_name, client\_token)}
    \begin{itemize}
        \item Service enforces client-token idempotency~\cite{awsidempotency}
        \item Tracks resource lifecycle
        \item Enforces per-principal quotas
    \end{itemize}
\end{enumerate}

\subsection{Fault Injection Points}

We inject faults (triggering checkpoint restore) at three critical points:

\begin{enumerate}
    \item \textbf{Before sending}: Checkpoint taken before HTTP request is sent
    \item \textbf{In-flight}: Checkpoint taken after sending but before receiving response
    \item \textbf{After response}: Checkpoint taken after receiving response but before agent persists ``done'' status
\end{enumerate}

Each injection point exercises different aspects of the state mismatch.

\subsection{Metrics}

\begin{itemize}
    \item \textbf{Duplicate commit rate}: Fraction of logical operations that produce multiple committed tool-side entries

    \item \textbf{Token reuse rate}: Fraction of ``single-use'' approvals/tokens accepted more than once after restore/fork

    \item \textbf{Fork amplification factor}: Ratio of committed actions under forked restores to the allowed bound

    \item \textbf{Mitigation overhead}: Added latency per tool call for any external logging/authorization checks (when evaluating defenses)
\end{itemize}

\subsection{Baselines}

We compare against:

\begin{enumerate}
    \item \textbf{No checkpoint/restore}: Baseline without any snapshotting

    \item \textbf{Deterministic replay/durable workflow style}: Record tool-call decisions and replay them rather than re-synthesizing after restore (reflecting durable execution assumptions)~\cite{temporal}

    \item \textbf{Framework time-travel}: Use LangGraph time-travel to resume from checkpoints and compare OS-level checkpointing~\cite{langgraph}
\end{enumerate}

\section{Related Work}

\subsection{Rollback and Forking Attacks in TEEs}

Rollback and forking attacks, and the notion of ``state continuity,'' are well studied in trusted execution settings. Memoir introduced practical state continuity for protected modules, establishing the theoretical foundation for understanding rollback vulnerabilities~\cite{memoir}. ROTE provided rollback protection for trusted execution environments, addressing both rollback and forking attack dimensions~\cite{rote}.

Our setting differs from TEE research in a crucial way: the target is an application-layer agent whose control flow and requests may be synthesized from natural language. This introduces non-determinism that is absent in the deterministic programs typically protected by TEEs.

\subsection{Agentic Systems and Exploration}

Recent systems work on agentic exploration motivates snapshot/restore and identifies external side effects as a key unresolved challenge~\cite{agenticexploration}. This work provides the systems foundation for agent exploration but does not frame external side effects as a concrete security vulnerability with measurable invariants.

\subsection{Agent Frameworks with Checkpointing}

Agent frameworks expose checkpointing/time travel as features. LangGraph provides persistent checkpoints and time-travel interfaces for agent graphs~\cite{langgraph}. These capabilities make restore/fork operations common in practice, increasing the attack surface for the vulnerabilities we describe.

\subsection{Agent Security Mechanisms}

Agent security mechanisms such as privilege-control and runtime enforcement focus on constraining tool use. Progent provides programmable privilege control for LLM agents~\cite{progent}, while AgentSpec offers customizable runtime enforcement~\cite{agentspec}. These approaches are largely orthogonal to checkpoint-induced rewind/fork semantics---they constrain what actions an agent can take, but do not address the state continuity problems that arise from checkpoint/restore.

\subsection{Prompt Injection and LLM Security}

OWASP documents prompt injection and insecure output handling among top risks for LLM applications~\cite{owaspllm}. While our work focuses on checkpoint/restore vulnerabilities rather than prompt injection, the two threat categories can interact: an attacker might use prompt injection to influence agent state in ways that are preserved across checkpoints.

\section{Conclusion}

Checkpoint/restore and time-travel execution are becoming standard building blocks for tool-using LLM agents, driven by operational needs (recovery, debugging) and algorithmic needs (branching exploration). Existing systems practice assumes deterministic replay or stable idempotency identities to keep external side effects safe under retry~\cite{temporal, stripeidempotency}. LLM agents weaken these assumptions: restore can rewind internal authorization and safety state while the external world does not rewind, and post-restore action synthesis can vary enough to defeat idempotency mechanisms.

We argue this creates a concrete, measurable security problem---replay of irreversible actions, revocation/consumption bypass, and fork-based authority amplification---and we provide a practical testbed design to reproduce and quantify these failures using CRIU~\cite{criu} and external tool services with append-only logs.

Our analysis reveals a fundamental tension: the features that make checkpoint/restore valuable for agent development (state preservation, branch exploration, failure recovery) are precisely the features that create security vulnerabilities when agents interact with external systems that maintain their own state.

Future work should explore:
\begin{itemize}
    \item External authorization services issuing short-lived, single-use capabilities verified at tool execution time
    \item Tool-side commit logs that can detect and reject replayed requests even with varying idempotency keys
    \item Semantic-aware checkpointing that captures the logical operation identity rather than just process state
    \item Coordination protocols between forked agent instances to prevent authority amplification
\end{itemize}

This paper identifies the security implications of checkpoint mechanisms for non-deterministic LLM-driven agents and outlines directions for future research.
