\begin{abstract}
	Checkpoint-restore mechanisms, increasingly adopted in LLM agent frameworks for both error recovery and exploration, reintroduce a classic systems challenge: externally visible outputs cannot be rolled back. Unlike traditional deterministic systems, tool-using LLM agents inherently rely on implicit execution context (e.g., permissions, quotas, external API state), and thus re-synthesize semantically equivalent but subtly different actions after restoring from checkpoints. This \emph{semantic drift} silently bypasses traditional at-most-once defenses such as idempotency keys and may revive consumed credentials, leading to what we term \emph{semantic rollback attacks}. We characterize two vulnerability classes, \emph{Action Replay} and \emph{Authority Resurrection}, and demonstrate their reproducibility in a proof-of-concept testbed with realistic external tool servers. We introduce \sys{} (Agent Checkpoint-Restore Fence), a runtime mechanism providing a \emph{fork-aware tool-effect journal} that captures execution context as stable effect fingerprints and enforces precise replay-vs-fork semantics upon restoration. In our evaluation, \sys{} completely eliminates semantic rollback vulnerabilities while preserving agents' flexibility for safe exploration of alternative execution paths.
\end{abstract}

\section{Background and Motivation}

\subsection{Checkpoint-Restore Mechanisms in Classical Systems}

Checkpoint-restore (CR) systems such as CRIU and Docker Checkpoint preserve local execution states (memory, file descriptors, and container-local filesystems~\cite{criu}) but do not provide transactional consistency for external resources (remote APIs, databases, network services). After restoration, external states previously altered by agent actions remain irreversibly modified, creating the \textit{output commit problem}~\cite{elnozahy2002survey, strom1985optimistic} as \emph{state divergence}. CR is increasingly employed not only for fault recovery but also for exploring alternative execution paths~\cite{xu2025agenticexploration}.

\subsection{LLM Agents and Their Need for Checkpoint-Restore}

LLM agents manage cloud resources, payments, and software engineering tasks~\cite{sweagent, openhands}. Agent frameworks expose persistent checkpoint-restore as a first-class feature~\cite{langgraph, langgraph_durable}; durable execution guidance warns that resumed execution may rerun side-effecting steps and recommends idempotency~\cite{langgraph_functional_idempotency}. However, ``idempotent'' is a \emph{caller-service contract} that presumes stable operation identity across retries. LLM agents fundamentally break this: after restore, they do not deterministically re-execute the same call but \emph{re-synthesize} a semantically equivalent call with different parameters, even under temperature=0~\cite{atil2025nondeterminism, khatchadourian2026replayable}. This \emph{semantic drift} means the runtime cannot rely on parameter identity to recognize replayed operations. Durable engines like Temporal record nondeterministic values for replay~\cite{temporal_side_effects}, but require deterministic workflow structure that LLM agents cannot provide.

\subsection{Related Work and Limitations of Existing Solutions}

\textbf{Durable workflows.} RPC at-most-once semantics~\cite{birrell1984rpc} are operationalized via idempotency keys~\cite{stripe_idempotent_requests, aws_ecs_idempotency, ietf_idempotency_key}. Durable engines record non-deterministic values for replay~\cite{temporal_side_effects}, but assume deterministic workflow structure.

\textbf{Agent replay and security.} Record-and-replay improves agent reliability~\cite{feng2025agentrR}; debugging tools support resetting conversations~\cite{ma2025dover}; security mechanisms enforce privilege control~\cite{progent, agentspec, owaspllm}. None address CR interaction with \emph{irreversible tool effects}.

\textbf{Snapshot anomalies.} TEE rollback protection~\cite{parno2011memoir, matetic2017rote} assumes deterministic programs. A Vault issue documents tokens reappearing after snapshot restore~\cite{vault_issue_28378}. No existing approach addresses transactional consistency of external environments across checkpoint boundaries.

We propose \sys{} (Agent Checkpoint-Restore Fence), a runtime mechanism that enforces fork-aware tool-effect semantics to prevent semantic rollback attacks.

\section{Threat Model}

We target two invariants: (1) no replay of irreversible effects across restores, and (2) revocation monotonicity (consumed credentials must not become reusable). We consider two attacker models: \emph{Checkpoint Abuse}, where an adversary exploits CR features exposed for exploration~\cite{langgraph}, analogous to TEE restart attacks~\cite{matetic2017rote}; and \emph{Fault-Triggered Restore}, where crashes trigger restoration and the attacker benefits from duplicate effects. Both imply transactional consistency of external operations across checkpoints, a requirement existing CR mechanisms fail to address.

\section{Attacks}

We identify two attack classes exploiting state divergence after restore. \emph{Action Replay} exploits idempotency key instability to enable duplicate commits (financial fraud, denial-of-wallet) and applies to both attacker models. \emph{Authority Resurrection} exploits consumed single-use tokens that reappear in rolled-back agent state to enable unauthorized operations, requiring Checkpoint Abuse where the attacker controls post-restore prompts.

\subsection{Action Replay Attack}
\label{sec:v1}

Figure~\ref{fig:action-replay} illustrates this attack. Idempotency keys are a caller-service contract: same key + same parameters yields the stored result; different parameters trigger conflict or rejection~\cite{stripe_idempotent_requests, aws_ecs_idempotency}. Semantic drift after restore violates this contract: the LLM regenerates a \emph{different} key for the \emph{same} logical operation, so the service treats it as a new request, enabling duplicate payments or resource provisioning.

\subsection{Authority Resurrection Attack}
\label{sec:v2}

Authority Resurrection exploits consumed tokens that reappear in rolled-back agent state. Without transactional context preservation, stateless validators (signature check only) incorrectly accept reused tokens; stateful validators (revocation list) reject them.

\section{Design: \sys}
\label{sec:design}

\sys{} interposes at the tool boundary (e.g., as an MCP proxy) and treats each \emph{irreversible} tool call as an \emph{effect} that must have a stable identity across restores. Rather than relying on the LLM to regenerate an identical idempotency key, \sys{} assigns each effect a stable \texttt{op\_slot} (a monotonic index within a run) and captures an \emph{effect receipt} including an \emph{Operational Semantic Fingerprint}:
$\langle \texttt{thread\_id}, \texttt{branch\_id}, \texttt{op\_slot}, \texttt{tool}, \texttt{fingerprint}, \texttt{req}, \texttt{resp} \rangle$
The fingerprint is a deterministic hash of the tool call's execution context. In our prototype, this comprises the canonical JSON of tool arguments; in a full deployment, it can be extended to incorporate external environment state such as filesystem snapshots, resource quotas, and permission validity.

\textbf{Replay vs.\ fork semantics.} Upon restore, if the agent issues an irreversible tool call at an \texttt{op\_slot} that already has a receipt, \sys{} automatically compares fingerprints: (i)~if they match, \sys{} returns the recorded response without reissuing the side effect (\emph{replay}); (ii)~if they differ, \sys{} blocks the call, surfaces the prior receipt as context, and requires an explicit fork (new \texttt{branch\_id}) before allowing a new effect. This mechanism is purely structural; it requires no runtime model inference or semantic similarity judgments, keeping the runtime simple, fast, and trustworthy. \sys{} thus defines transactional checkpoint boundaries at each irreversible tool call, ensuring either replay of the committed effect or an explicit fork to a new execution branch.

\textbf{Credential monotonicity.} For single-use approvals, \sys{} records token consumption in effect receipts. Combined with stateful server-side validation (which rejects reused tokens~\cite{vault_issue_28378}), this prevents Authority Resurrection. We leave full branch management and richer environment-context fingerprinting to future work.

\section{Proof-of-Concept Evaluation}

\textbf{Experimental Setup.} We build a proof-of-concept testbed using Claude Code CLI backed by Qwen3-32B, with CR simulated via session truncation. External services are MCP servers: a bank (\texttt{transfer} with UUID idempotency), cloud provider (\texttt{create\_server}), and approval service (stateless/stateful validation). Checkpoints are placed after verification but before commit.

\textbf{Results.} Without \sys{}, all 20 CR trials produced duplicate commits due to key instability; with \sys{}, fingerprint-based replay-vs-fork semantics eliminate all duplicates. For Authority Resurrection, stateless validation accepted reused tokens for unauthorized targets (2/2); stateful validation rejected all.

\textbf{Limitations.} Our testbed simulates CR via session truncation rather than CRIU, sample sizes are limited, and we evaluate one model family (Qwen3-32B). The fork-conflict path (fingerprint mismatch) is validated manually rather than at scale.

\section{Discussion and Conclusion}

Checkpoint-restore for LLM agents requires transactional semantics for external environments, a requirement neglected by approaches assuming deterministic replay~\cite{temporal_side_effects, langgraph_durable}. Our experiments show that semantic drift inevitably occurs across restores, silently breaking idempotency contracts. \sys{} addresses this by capturing execution context as operational fingerprints and enforcing replay-vs-fork semantics at each irreversible tool call. Crucially, post-restore divergence can be legitimate exploration rather than harmful drift, provided it is explicitly identified and managed. \sys{} represents a step towards safe, transactionally consistent checkpoint-restore for tool-using LLM agents.
