\title{Semantic Rollback Attacks on Checkpoint-Restore in LLM-Driven Agents}

\begin{abstract}
Checkpoint-restore mechanisms, increasingly adopted in LLM agent frameworks for fault tolerance and exploration, reintroduce a classic distributed systems challenge: the output commit problem. Unlike deterministic workflows where logged outputs enable consistent replay, LLM agents produce non-deterministic yet semantically equivalent actions upon restoration, causing state divergence between rolled-back agent state and persistent external state. This semantic drift defeats traditional idempotency mechanisms. We identify two vulnerability classes: (1) Action Replay, where post-restore action synthesis generates different idempotency keys, bypassing duplicate detection and enabling financial fraud; and (2) Authority Resurrection, where consumed single-use tokens are unintentionally revived after restore. Our proof-of-concept experiments demonstrate that action duplication and token reuse consistently occur under common configurations. We present \sys{}, a runtime mechanism that maintains stable operation identities across restores, reducing duplicate commits to zero in our evaluation.
\end{abstract}

\section{Background and Motivation}

\subsection{Checkpoint-Restore Mechanisms}

Checkpoint-restore (CR) enables saving process state to disk and later resuming execution. CRIU~\cite{criu} can freeze Linux processes or containers, capturing memory, registers, file descriptors, and network connections. Upon restoration, the process resumes from the exact checkpoint, unaware that time has passed or external state may have changed. This creates a classic distributed systems challenge: the \textit{output commit problem}~\cite{elnozahy02survey, stromyemini85}. External outputs (payments, API calls) cannot be rolled back, so systems must ensure outputs are not duplicated or lost after recovery. Traditional solutions assume piecewise-deterministic execution with logged outputs for replay.

\subsection{Checkpoint-Restore in Agent Frameworks}

Large-language-model (LLM) agents are increasingly deployed in production settings, managing cloud resources, processing payments, and automating software engineering tasks~\cite{sweagent, openhands}. These deployments demand reliable fault tolerance and debugging capabilities. The Kubernetes community is actively developing container checkpoint capabilities~\cite{k8scheckpoint}. Agent frameworks like LangGraph now provide persistent checkpoints and time-travel interfaces as first-class features~\cite{langgraph, langgraphdurable}, while agentic exploration research treats backtracking as essential for agent reasoning~\cite{agenticexploration}.

However, LLM agents violate the determinism assumption required by traditional CR. Their runtime synthesis from natural-language prompts produces non-deterministic yet semantically equivalent behaviors~\cite{llmnondeterminism}, even with temperature=0 settings. Durable execution engines like Temporal explicitly require workflow code to be deterministic~\cite{temporal}; LLM agents cannot provide this guarantee, creating critical mismatches where an agent's restored state no longer aligns with irreversible external states such as committed payments or consumed credentials.

\subsection{Existing Solutions and Their Limitations}

RPC systems traditionally provide at-most-once semantics through request identifiers~\cite{birrellnelson84}. Payment and cloud APIs implement this via idempotency keys~\cite{stripeidempotency, awsidempotency}, assuming callers reliably reuse stable keys. This assumption fails when keys are synthesized non-deterministically by LLM agents. Rollback attacks and state continuity are well studied in trusted execution environments~\cite{memoir, rote}, but these focus on deterministic programs. Agent security mechanisms including privilege control~\cite{progent} and runtime enforcement~\cite{agentspec} constrain what actions agents can take but do not address state continuity problems from checkpoint-restore. While OWASP documents prompt injection risks~\cite{owaspllm}, this paper identifies a distinct vulnerability class: \textit{semantic rollback}, where the combination of LLM non-determinism and checkpoint-restore causes the output commit problem to manifest as security violations. We present \sys{}, a runtime mechanism that maintains stable operation identities across restores to mitigate these vulnerabilities.

\section{Threat Model}

\subsection{Security Goals}

We focus on invariants that are standard in durable, side-effecting systems:

\begin{itemize}
    \item \textbf{No replay of irreversible effects}: Restoring or retrying should not commit a payment, ticket, or resource creation more than once for the same logical operation.

    \item \textbf{Revocation monotonicity}: Once credentials or approvals are revoked or consumed, restore must not make them usable again.
\end{itemize}

\subsection{Attacker Models}

We consider two attacker models. In \textbf{Fault-Triggered Restore}, the agent is checkpointed for recovery; crashes or OOM kills trigger restoration. The attacker only influences inputs (emails, documents) and benefits from outcomes (duplicate payments); no special access is required. In \textbf{Time-Travel Abuse}, the platform exposes time travel as a feature~\cite{langgraph}, and an adversary (authenticated user or legitimate workflow) may trigger security violations, analogous to restart attacks in TEE literature~\cite{rote}.

\subsection{Out of Scope}

We do not assume compromise of cryptographic primitives, the checkpoint mechanism itself, physical access to the execution environment, or modification of the agent's code or model weights.

\section{Attacks}

The root cause of semantic rollback vulnerabilities is state divergence: checkpoint-restore rolls back the agent's internal state (memory, credentials, task progress), but external services (payment processors, cloud APIs, Git platforms) retain their state. Combined with LLM non-determinism, the agent re-synthesizes tool calls with different parameters (including different idempotency keys), causing external services to treat replayed requests as new operations. We identify two attack classes: (1) Action Replay, where post-restore action synthesis generates different idempotency keys, bypassing duplicate detection and enabling financial fraud or denial-of-wallet attacks; and (2) Authority Resurrection, where consumed single-use tokens are revived after restore, enabling unauthorized operations under stateless validation. Action Replay applies to both attacker models (no post-restore control needed), while Authority Resurrection requires Time-Travel Abuse where the attacker controls post-restore prompts.

\subsection{Action Replay Attack}
\label{sec:v1}

Figure~\ref{fig:action-replay} illustrates this attack. If a checkpoint is taken before an external commit is durably recorded, restoring can re-execute the same operation. This enables denial-of-wallet (crash after resource provisioning inflates victim's bill) and financial fraud (time-travel after receiving service to avoid payment).

In classic durable execution, idempotency keys prevent duplicates~\cite{temporal, stripeidempotency}. In LLM agents, the key is not stable across restores: the agent regenerates different idempotency keys, causing duplicate payments, tickets, or resource provisioning. In software engineering agents, different branch names or PR titles result in duplicate PRs. The attack succeeds when two committed entries exist for the same logical operation.

\subsection{Authority Resurrection Attack}
\label{sec:v2}

Figure~\ref{fig:authority-resurrection} illustrates this attack. Agents hold credentials or single-use approvals in memory. Restoring a checkpoint reintroduces consumed tokens, enabling reuse attacks. Real systems exhibit this: a Vault issue showed single-use tokens reappearing after raft snapshot restore~\cite{vaultissue}.

Exploitability depends on the validation model. With stateless validation (signature check only), tokens are accepted if cryptographically valid. With stateful validation (revocation list), reuse is rejected. The attack succeeds when a consumed token is accepted after restore.

\section{Evaluation}

\subsection{Experimental Setup}

We evaluate semantic rollback vulnerabilities through proof-of-concept experiments. Our testbed uses Claude Code CLI backed by Qwen3-32B, with checkpoint-restore simulated via session file truncation (mirroring application-level time-travel features like LangGraph). External services are MCP servers with append-only logs: a bank (\texttt{transfer} with UUID idempotency), cloud provider (\texttt{create\_server}), and approval service (configurable stateless/stateful validation). Checkpoints are placed after verification (e.g., \texttt{check\_balance}) but before commit (e.g., \texttt{transfer}), the most vulnerable point. We test four scenarios: bank transfer, cloud provisioning, approval-based deletion, and payment. As baseline, we truncate sessions \textit{after} the action to confirm duplication requires checkpoint-restore timing.

\subsection{Results}

\textbf{Action Replay.} All 20 checkpoint-restore trials (10 transfer, 10 cloud) exhibited key instability and action duplication: the LLM regenerated different idempotency keys after restore, causing duplicate commits in every case. All 10 baseline trials showed 0\% duplication, confirming the vulnerability stems from checkpoint timing, not agent behavior.

\textbf{Authority Resurrection.} We tested token reuse under three validation modes (2 trials each): stateless (signature-only), stateful\_sync (immediate revocation check), and stateful\_async (delayed check). With stateless validation, consumed tokens were accepted for unauthorized targets in 2/2 approval trials (deleting Bob's data with Alice's token). Stateful validation (both sync and async) successfully rejected reuse in all approval trials (0/2 vulnerable). Payment scenarios showed mixed results requiring larger sample sizes.

\subsection{Limitations}

Our testbed simulates checkpoint-restore via session truncation rather than OS-level mechanisms like CRIU; future work should validate with process-level checkpointing. Sample sizes are limited (10--20 trials for Action Replay, 2 for Authority Resurrection), and we evaluate only one model family (Qwen3-32B). Task prompts explicitly request UUID generation, potentially inflating key instability rates.

\section{Mitigation Strategies}

For Action Replay, agent frameworks should persist idempotency keys to durable storage before tool calls and reload them after restore, ensuring key stability across restores; external services should implement semantic-level deduplication based on operation identity rather than relying solely on caller-provided keys. For Authority Resurrection, services should use synchronous stateful token validation (checking consumption state in real-time) rather than stateless JWT-only validation, and issue short-lived tokens to minimize the attack window. At the framework level, agent systems should define explicit checkpoint-safe boundaries ensuring external commits are recorded in agent state before checkpointing, and provide restore hooks that re-validate credentials and check for already-committed actions upon restore.

\section{Conclusion}

Checkpoint-restore primitives are becoming standard in LLM agent frameworks, yet their integration creates measurable security vulnerabilities. LLM non-determinism means post-restore action synthesis varies enough to defeat idempotency mechanisms, while agent state rollback does not affect external systems, enabling action replay and authority resurrection attacks. Our proof-of-concept experiments demonstrate these failures under common configurations, with duplication and token reuse consistently observed in tested scenarios. Mitigating these vulnerabilities requires rethinking the checkpoint-restore abstraction for non-deterministic agents, potentially through external capability verification at execution time, tool-side commit logs resilient to key variation, or semantic-aware checkpointing that preserves logical operation identity.
