\begin{abstract}
	Checkpoint-restore mechanisms, increasingly adopted in LLM agent frameworks for both error recovery and exploration, reintroduce a classic systems challenge: externally visible outputs cannot be rolled back. Unlike traditional deterministic systems, tool-using LLM agents may depend on implicit execution context (e.g., user permissions in prompt, quotas, external API state), and re-synthesize semantically equivalent but subtly different actions after restoring from checkpoints. This \emph{semantic drift} silently bypasses traditional at-most-once defenses such as idempotency keys and may revive consumed credentials, leading to what we term \emph{semantic rollback attacks}. We characterize two vulnerability classes, \emph{Action Replay} and \emph{Authority Resurrection}, and demonstrate their reproducibility in a proof-of-concept testbed with realistic external tool servers. We introduce \sys{} (Agent Checkpoint-Restore Fence), a framework-agnostic runtime mechanism providing a \emph{fork-aware tool-effect journal} that enforces safe replay-or-fork semantics for external tool calls. \sys{} captures tool-call context as stable effect fingerprints via eBPF and reliably distinguishes replay from exploration upon restoration. We demonstrate \sys{} can eliminate semantic rollback vulnerabilities while preserving agents' flexibility for exploration of alternative execution paths.
\end{abstract}

\section{Background and Motivation}

\textbf{Checkpoint-restore (CR).} Checkpoint-restore (CR) systems such as CRIU and Docker Checkpoint preserve local execution states (memory, file descriptors, and container-local filesystems~\cite{criu,mvvm}) but do not provide transactional consistency for external resources (remote APIs, databases, network services). After restoration, external states previously altered by agent actions remain irreversibly modified, a manifestation of the classic \textit{output commit problem}~\cite{elnozahy2002survey, strom1985optimistic}. CR is increasingly employed not only for fault recovery but also for exploring alternative execution paths~\cite{xu2025agenticexploration}, yet mainstream agent frameworks provide only conversation-level checkpoints without consistency guarantees for external operations.

\textbf{LLM Agents real world CR issue.} LLM agents manage cloud resources, payments, and software engineering tasks~\cite{sweagent, openhands}. Agent frameworks expose persistent checkpoint-restore as a first-class feature~\cite{langgraph, langgraph_durable}; their guidance warns that resumed execution may rerun side-effecting steps and recommends idempotency~\cite{langgraph_functional_idempotency}. However, ``idempotent'' is a \emph{caller-service contract} that presumes stable operation identity across retries. LLM agents fundamentally break this: after restore, they do not deterministically re-execute the same call but \emph{re-synthesize} a semantically equivalent call with different parameters, even under temperature=0~\cite{atil2025nondeterminism, khatchadourian2026replayable}. This \emph{semantic drift} means the runtime cannot rely on parameter identity to recognize replayed operations. Durable engines like Temporal record nondeterministic values for replay~\cite{temporal_side_effects}, but require deterministic workflow structure that LLM agents cannot provide.  A Vault issue documents single-use tokens reappearing after snapshot restore~\cite{vault_issue_28378}, illustrating the problem in practice. 

\textbf{Related Work.} Effect journaling for safe replay has precedents in I/O tabling~\cite{somogyi2003iotabling} and durable execution engines~\cite{birrell1984rpc, temporal_side_effects}; together with idempotency protocols~\cite{stripe_idempotent_requests, ietf_idempotency_key}, these all assume deterministic caller behavior, as discussed above. Agent record-and-replay improves reliability~\cite{feng2025agentrR} and version-control systems provide rollback and branching for agent traces~\cite{li2025agentgit}, but neither addresses irreversible external effects during replay. Security mechanisms enforce privilege control for agents~\cite{progent, agentspec, owaspllm} without considering checkpoint-restore interactions. TEE rollback protection~\cite{parno2011memoir, matetic2017rote} assumes deterministic programs. No existing work treats non-deterministic LLM re-synthesis after restore as a security attack surface or provides framework-agnostic protection for irreversible tool effects.

\section{Threat Model}

We target two invariants: (1) no replay of irreversible effects across restores, and (2) revocation monotonicity (consumed credentials must not become reusable). We consider two attacker models: \emph{Deliberate Rollback Abuse}, where an adversary exploits CR features exposed for exploration~\cite{langgraph}, analogous to TEE restart attacks~\cite{matetic2017rote}; and \emph{Crash-Induced Restore}, where crashes trigger restoration and the attacker benefits from duplicate effects. Both require that external operations remain consistent across checkpoints.

\section{Attacks}

We identify two attack classes exploiting state divergence after restore. \emph{Action Replay} exploits idempotency key instability to enable duplicate commits (financial fraud, denial-of-wallet) and applies to both attacker models. \emph{Authority Resurrection} exploits consumed single-use tokens that reappear in rolled-back agent state to enable unauthorized operations, requiring Deliberate Rollback Abuse where the attacker controls post-restore prompts.

\textbf{Action Replay.}\label{sec:v1} Figure~\ref{fig:action-replay} illustrates this attack. As described above, idempotency keys require stable parameters across retries~\cite{stripe_idempotent_requests, aws_ecs_idempotency}. Semantic drift after restore violates this: the LLM regenerates a \emph{different} key for the \emph{same} logical operation, so the service treats it as a new request, enabling duplicate payments or resource provisioning.

\textbf{Authority Resurrection.}\label{sec:v2} This attack exploits consumed tokens that reappear in rolled-back agent state. Without context preservation, the agent does not know the token was already used and attempts to reuse it. Stateless validators (signature check only) incorrectly accept such reuse; stateful validators (revocation list) reject it, but the agent remains in an inconsistent state, unaware its credential is invalid.

\section{Design: \sys}
\label{sec:design}

\sys{} interposes at the tool boundary (e.g., as an MCP proxy) and treats each \emph{irreversible} tool call as an \emph{effect} that must have a stable identity across restores. Rather than relying on the LLM to regenerate an identical idempotency key, \sys{} captures an \emph{effect receipt} for each effect, keyed by an \emph{Operational Semantic Fingerprint}:
\begin{small}
\[\langle \texttt{thread\_id}, \texttt{branch\_id}, \texttt{tool}, \texttt{fp}, \texttt{req}, \texttt{resp} \rangle\]
\end{small}
The fingerprint captures the implicit context needed to identify the intended semantic operation, enabling precise replay-or-fork decisions across restores. In our prototype, fingerprints comprise canonical tool arguments, supplemented by eBPF-based system-level monitors~\cite{zheng2025agentsight} that capture external environment state (filesystem changes, shell commands, and MCP tool calls). Because context is captured at the OS level rather than through agent instrumentation, \sys{} requires no agent framework modifications.

\textbf{Replay vs.\ fork semantics.} Upon restore, if the agent issues an irreversible tool call whose fingerprint matches an existing receipt, \sys{} applies replay-or-fork: (i)~if they match, \sys{} returns the recorded response without reissuing the side effect (\emph{replay}); (ii)~if they differ, \sys{} blocks the call, surfaces the prior receipt as context, and requires an explicit fork (new \texttt{branch\_id}) before allowing a new effect. This mechanism is purely structural; it requires no runtime model inference or semantic similarity judgments, keeping the runtime simple, fast, and trustworthy. \sys{} thus treats each irreversible tool call as a checkpoint boundary, ensuring either replay of the committed effect or an explicit fork to a new execution branch.

\textbf{Credential monotonicity.} For single-use approvals, \sys{} records token consumption in effect receipts so the agent is informed before attempting reuse, avoiding both unauthorized actions (stateless validators) and inconsistent agent state (stateful validators)~\cite{vault_issue_28378}. Full branch management and richer fingerprinting remain future work.

\section{Proof-of-Concept Evaluation}

\textbf{Experimental Setup.} We build a proof-of-concept testbed using Claude Code CLI backed by Qwen3-32B, with CR simulated via session truncation. External services are MCP tool servers: a bank (transfer with UUID idempotency), a cloud provider (server creation), and an approval service (stateless/stateful). Checkpoints are placed after verification but before commit. The fork-conflict path (fingerprint mismatch) is validated manually rather than at scale.

\textbf{Results.} Without \sys{}, all 20 CR trials produced duplicate commits due to key instability; with \sys{}, fingerprint-based replay-vs-fork semantics eliminate all duplicates. For Authority Resurrection, stateless validation accepted reused tokens for unauthorized targets (2/2); stateful validation rejected all; with \sys{}, token reuse was blocked regardless of validator mode (0/2).

\section{Discussion and Conclusion}

Our experiments show that semantic drift inevitably occurs across restores, silently breaking idempotency contracts~\cite{temporal_side_effects, langgraph_durable}. \sys{} addresses this by capturing execution context as operational fingerprints and enforcing replay-vs-fork semantics at each irreversible tool call. Unlike durable execution engines and I/O tabling approaches~\cite{somogyi2003iotabling, temporal_side_effects} that assume deterministic callers, our approach recognizes that post-restore divergence can be legitimate exploration rather than harmful drift, and explicitly accommodates it through precise fork semantics. \sys{} represents a step towards safe checkpoint-restore for tool-using LLM agents.
