## 4. 实验结果

### 4.1 实验 1 结果

| 场景 | Duplicate Rate | Ref 变化 | 攻击者获益 |
|------|---------------|----------|-----------|
| V1-TM1 转账双花 | 100% | 0% (相同 ref) | $500 |
| V1-TM2 云资源重复 | 100% | 0% (相同 token) | $3/hour |
| Baseline (无 CR) | 0% | N/A | $0 |

**观察**:
- idempotency key (ref/client_token) **没有变化**
- 但双花仍然成功
- 原因: MCP 服务器每次调用都是新进程，没有保存第一次操作的状态

### 4.2 实验 2 结果

| 验证模式 | 审批绕过 | 支付欺诈 |
|---------|---------|---------|
| Stateless | 100% 漏洞 | 100% 漏洞 |
| Stateful_sync | 100% 漏洞* | 100% 漏洞* |
| Stateful_async | 100% 漏洞 | 100% 漏洞 |

**\* 注意**: Stateful_sync 也显示漏洞是因为 MCP 服务器状态不跨进程持久化

## 5. 关键问题与诚实评估

### 5.1 这是真正的安全问题吗？

**是的，但有限制条件**:

✅ **真实的安全问题**:
1. Agent 状态回滚 + 外部状态不回滚 = 状态分歧（这是核心漏洞）
2. LLM 的非确定性可能导致不同的 idempotency key
3. 单次授权 token 可能被用于多个操作

❌ **当前实验的局限性**:

1. **MCP 服务器状态问题**:
   - 每次 `claude` 调用启动新的 MCP 服务器进程
   - 状态不跨进程持久化
   - 所以即使用相同的 ref，第二次也能成功
   - **这掩盖了真正的 V1 漏洞机制**（应该是不同的 ref 绕过 idempotency）

2. **Prompt 引导问题**:
   - V2 实验中，攻击者的 prompt 明确告诉 agent 用 token 执行不同操作
   - 这是否是现实的攻击场景？需要讨论

3. **未验证真实 /rewind**:
   - 我们模拟的是 session 文件截断
   - 需要验证这是否等同于 Claude Code 的 /rewind 功能

### 5.2 符合安全论文要求吗？

| 要求 | 当前状态 | 建议改进 |
|------|---------|---------|
| 明确的威胁模型 | ✅ 有 TM1/TM2 | 需要更详细描述攻击者能力 |
| 可重复的实验 | ✅ 代码可运行 | 需要更多试验次数 |
| 真实的攻击场景 | ⚠️ 部分 | 需要验证真实 /rewind |
| 漏洞根因分析 | ⚠️ 部分 | 需要分离 V1 的两个因素 |

## 7. 结论

### 当前实验证明了什么？

1. **状态分歧存在**: Agent 状态可以回滚，而外部状态不能
2. **V2 漏洞更清晰**: 单次授权 token 可用于多个操作（在 stateless 验证下）
3. **V1 漏洞需要更多工作**: 当前的 idempotency key 没有变化，漏洞来自服务器状态问题
