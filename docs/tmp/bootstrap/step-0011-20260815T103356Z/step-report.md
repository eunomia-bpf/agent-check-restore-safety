# Step 0011: real Codex call survives control replacement

Date: 2026-08-15 UTC

## Outcome

A real model reached through the locally logged-in Codex App Server invoked one
strict application tool. The payment service durably committed the Operation
and dropped its first response. While the App Server callback remained pending,
the complete Go control process was terminated and replaced. The new process
reopened the same History, retried the same Operation, validated the payment
receipt, and returned it to Codex. Codex completed the turn with exactly
`DONE`.

Payment observed two deliveries and one durable commit. A third execution of
the settled Operation was returned from History with `reused=true` and did not
reach payment.

## Reproduction

```sh
python3 -m adapter.codex_runtime_demo \
  --output-dir docs/tmp/bootstrap/step-0011-20260815T103356Z
```

The public entry point is:

```sh
make runtime-codex-demo
```

This target is deliberately absent from `runtime-verify`; only an explicit
command can use the logged-in account.

## Concrete boundaries

- Codex App Server: real `codex-cli 0.147.0`, authenticated through the existing
  ChatGPT login; no mock model endpoint and no custom model provider.
- Agent workspace: empty temporary directory, read-only sandbox with
  `networkAccess=false`, no approvals, MCP servers, apps, or plugins.
- Control: separately built Go process with private adapter and administration
  credentials, durable History, and a head anchor outside the History directory.
- Payment: separate Go process and synced durability file outside the control
  process.
- Model-visible interface: one ephemeral thread and one strict
  `protected_payment` tool accepting only `codex-order-A-17`.

The implementation follows the official [Codex App Server protocol](https://learn.chatgpt.com/docs/app-server)
and was checked against the version-specific schema generated by:

```sh
codex app-server generate-json-schema --experimental --out DIR
```

## Identity binding

The App Server `callId` identifies one provider callback and is retained only as
protocol evidence. It is not used as the stable Operation identity. The
application-selected value is:

```text
effect_id = codex-order-A-17
call_id   = protected_payment/v1/codex-order-A-17
```

The authenticated adapter domain and call identity deterministically produce:

```text
op-9f20f3b6cf55834925b6ce5685cf6ffb80bb6397092e5f102e43d2bd7f2a7563
```

The tool schema, callback validation, both network attempts, remote receipt,
and final History all bind the same identity and payment bytes.

The control PID changed from `1421253` to `1421454` while the tool callback was
pending. The final Operation has `dispatch_generation=2` and
`phase=succeeded`. A credential scan found no bearer token, API key, or secret
in the retained evidence; token-usage telemetry in the App Server trace is not
an authentication token.

## Honest boundary

This run proves a real Codex model, real App Server callback, real process
replacement, real HTTP response loss, durable recovery, and one remote commit.
It does not yet place Codex and payment in disjoint network namespaces. The
existing Docker and QEMU experiments enforce that boundary independently. The
next system increment is to compose the live Codex path with the isolated
container network so the model-side process cannot address payment at all.

No file under `docs/paper/` changed in this step.
