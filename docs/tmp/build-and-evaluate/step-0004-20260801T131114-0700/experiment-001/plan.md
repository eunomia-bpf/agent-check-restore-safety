# Experiment Plan: RQ3 Concrete Runtime Refinement

## Research Question

- RQ exactly as written in the paper plan: **RQ3: Does the abstract invariant refine a real agent lifecycle?** Which facts must a concrete runtime expose so checkpoint, exclusive/parallel fork, selection, abort, replace/live restore, merge, revocation, uncertain dispatch, and settlement preserve authority continuity?
- Specific uncertainty tested here: whether a client frontend that owns Codex App Server's dynamic-tool dispatch, backed by a separately killable durable controller worker, can recover the topology, authority lineage, stable effect identity, and effect phase needed to map the fixed C01--C20 histories to admitted abstract steps, including the remote-success-before-controller-commit crash window.
- Why the answer matters: complete mediation and concrete/abstract correspondence are the strongest remaining premises of the paper's conditional trace theorem. Product hooks or transcript evidence do not establish either premise.

## Paper-Value Admission

- Planned role: **decisive** evidence for RQ3; runtime engineering and smoke checks are dependencies inside this experiment.
- Largest credible paper story this experiment could unlock: the finite abstract lifecycle is not merely analogous to current agents; one real App Server client can own a protected effect path and emit enough durable evidence to instantiate its conditional refinement theorem over fork, restore, merge, revocation, crash, retry, and settlement.
- Strongest reviewer reject argument or load-bearing uncertainty addressed: the abstract invariant assumes truthful lifecycle topology, stable claim/effect bindings, complete protected-effect mediation, crash-atomic durability, and queryable aggregate sink outcomes, but the current paper implements none of these in a real runtime boundary.
- Independent evidence added beyond existing runs and published results: the existing Python explorer and Lean development validate only abstract finite states. This experiment crosses the native Codex JSON-RPC `item/tool/call` boundary, exercises native `thread/fork` lineage, kills and restarts adapter processes at fixed sites, and compares persisted controller state with a separately persisted sink and independent oracle.
- Why the result is not tautological, already settled, or dominated: native request ownership, process-crash windows, sink reconciliation, and provider/runtime identifiers can falsify the mapping even when the abstract checker is correct. The oracle uses suite expectations and sink before/after snapshots rather than the controller's verdict.
- Paper decision if positive: report narrow deployed-runtime refinement evidence for one protected mock service, while retaining explicit limits on native Restore/Merge semantics, natural-language binding, arbitrary tools, and dishonest/non-queryable sinks.
- Paper decision if contradictory, mixed, or inconclusive: retain the abstract theorem but identify the failed refinement premise and state deployment as future work; a duplicate outcome, bypass, wrong P3 decision, or unreconstructable concrete edge directly falsifies the tested runtime instantiation, not the abstract mathematical theorem.
- Best alternative experiment and why this one has higher decision value: a full public trace scan can measure workload prevalence and field absence but cannot label authority violations or dispatch truth. An O0/O1/O2 theorem package is potentially useful only after the concrete event algebra is fixed and otherwise risks restating the existing observation-fiber lemma or logging checker state by definition.

## Expected And Alternative Outcomes

- Current expected answer: with the protected sink reachable only through the client-owned dynamic-tool handler, P3 will match the independent oracle on C01--C20, admit no unsafe history, produce at most one aggregate outcome per stable `effect_id`, and yield a replayable abstract edge sequence. Ordinary O0/O1 telemetry will retain three predeclared mixed-label fibers; O2 will not.
- Strongest competing explanation: App Server exposes correlation and fork identifiers but not a trustworthy lifecycle contract; native call/fork events plus adapter-defined Restore/Merge may be too weak to justify a concrete-refinement claim, or crash recovery may reveal an unmodeled phase.
- Result that would contradict the expectation: any protected sink write outside a matching handler request; any P3/oracle disagreement; any duplicated aggregate outcome; any missing stable binding; any C01--C20 concrete edge that cannot be classified as an exact admitted abstract label or zero-outcome stutter; any O2 mixed-label fiber/decoder failure; or any lost/hung App Server callback after a controller-worker crash.

## Published Precedent And Real Assets

- Closest published protocol: crash-consistency litmus testing with process termination at named persistence boundaries, stable idempotency keys, and recovery by querying the external service. This is a lifecycle-refinement study, not an LLM benchmark.
- Official system/model/data/benchmark/tool and version: installed OpenAI `codex-cli 0.146.0`; its generated experimental App Server v2 schemas; native `thread/start`, `thread/fork`, `turn/start`, and server-to-client `item/tool/call`; local Python 3.12 and SQLite. The runtime lock records binary hash, version, generated-schema hash, enabled experimental capability, host, and source reference.
- What is reused: the real Codex App Server binary and protocol. A deterministic local Responses-API stub follows the official App Server test pattern and emits a fixed function call, avoiding model stochasticity and network/model cost while preserving the real App Server tool-dispatch path.
- Necessary deviations or custom glue: the authority controller, mock sink, crash supervisor, oracle, and JSON-RPC client are project code. Codex supplies native history/fork IDs, but replace/live Restore and Merge are explicitly adapter APIs: Restore materializes a native fork from one source boundary and atomically retires or retains the source; Merge operates over real history IDs under a supplied projection. They are not claimed as native Codex semantics.

## Comparison

- Proposed system or method: `P3 authority-continuity`, with correlated admission, stable pre-dispatch tickets, durable phase transitions, adapter-owned topology operations, and receipt reconciliation.
- Main baseline 1: `P1 split-all`, representing nonduplicating capability partition at every fork. A matched run is needed because its safety but loss of late-bound choice depends on the same lifecycle/crash suite. If it matches P3 on both safety and accepted safe histories, the claimed practical value of topology-sensitive sharing is bounded.
- Main baseline 2: `P2 parent-escrow`, representing the strongest simple alternative for pure choose-one exploration. A matched run is needed to expose exactly which protected pre-selection operations and multi-lineage merges it rejects. If it matches P3, topology-conditioned advance reservations add no value on this workload.
- Controls or ablations, labeled separately: `P0 workspace/topology-local` is a known-incomplete topology/rollback null control; O0/O1/O2 are information ablations, not policies; direct sink access without the unforgeable adapter token is a negative mediation control; malformed/stale replay records and duplicate effect IDs are checker controls. Under the worker-only crash scope, the live frontend retains the same pending App Server `callId`, so P0 uses that actual ID and may be de-duplicated by the sink. The runner must not synthesize a fresh provider call ID. P0 is expected to expose authority resurrection/topology errors, not duplicate-on-full-client-loss.
- Conclusion if each main baseline matches or wins: P1 matching eliminates the demonstrated permissiveness benefit; P2 matching reduces the useful scope to cases already handled by escrow; either baseline producing fewer unsafe outcomes than P3 invalidates the P3 implementation or oracle.
- Information, tuning, and compute fairness: all P0--P3 runs use the same C01--C20 specifications, native runtime version, deterministic Responses stub, crash sites, sink, effect IDs, and oracle. A baseline that rejects a prerequisite records its earliest divergence; the runner never fabricates a later state.
- Split or leakage rule when relevant: the suite and oracle expectations are frozen before implementation in a separate read-only oracle fixture derived from the pre-existing L1/L8/L10/L13 matrix and abstract LTS. At launch, `codex_litmus` strips all expected labels, terminal states, and abstract-edge fixtures and gives each controller worker only the declarative operation stream, policy name, fault site, and opaque case ID. Controller workers cannot import oracle/replay-checker modules, read the oracle fixture, or inspect sink post-state except through the declared authenticated recovery query. Only `check_results` joins raw controller outputs with the separate oracle and independent sink snapshots. O0--O2 are projected from complete oracle-labeled histories rather than policy-truncated runs.

## Workloads And Metrics

- Real workloads or tasks: the fixed C01--C20 matrix in `docs/runtime-integration.md`. Every run that reaches a protected dispatch traverses the real App Server dynamic-tool flow. Native forks ground fork/restore histories; adapter APIs ground the declared retirement/retention and merge projection. For the effect-phase observation pair, C02 is observed after a before-dispatch crash with `J(e1)=prepared`, while C04 is observed after durable settlement but before the tool reply with `R(e1)` present. The identical normalized request is specifically permission to perform the physical `.attempt(e1,c1)`: C02 admits `Dispatch(e1)` and emits that label after recovery; C04 denies any new attempt and returns the cached receipt as a zero-outcome stutter.
- Primary metrics: (1) P3 decision agreement with the independent oracle out of 20; (2) admitted unsafe histories; (3) duplicate aggregate sink outcomes per stable `effect_id`; (4) concrete-edge replay coverage and first unmapped edge; (5) protected sink writes with no matching App Server handler request.
- Correctness check or ground truth: predeclared L1/L8/L10/L13 expectations plus sink before/after snapshots and authenticated receipts, stored separately from executable case operations. A separate replay checker reconstructs genesis, abstract labels, successor state hashes, and decisions from O2 and checks each edge against an independent transition implementation. The existing Lean theorem supplies the unbounded conditional implication; this run does not pretend that a Python replay check is a new mechanized proof.
- Repetitions, seeds, and uncertainty: correctness is deterministic and each of 20 cases is run once under each of four policies (80 terminal policy runs). The real preflight may be attempted at most three times. No statistical safety claim is made. Timing is secondary and deferred to RQ4 unless correctness completes; any later latency distribution uses fresh repetitions and is not inferred from these 80 cases.
- Cost estimate when material: no production credential, external account, third-party state, or paid/stochastic model turn. All effects target an isolated local sink; the deterministic model stub emits only the registered protected function call.

## Execution

- Authoritative workflow: `python -m adapter.codex_litmus --suite adapter/litmus.yaml --runtime-lock adapter/runtime-lock.json --raw-dir adapter/results/raw --output adapter/results/litmus.json`, followed by `python -m adapter.check_results --suite adapter/litmus.yaml --input adapter/results/litmus.json`.
- Real preflight case: keep the installed `codex app-server` and its JSON-RPC frontend alive, negotiate experimental API, create a thread with one registered protected dynamic tool, and let a deterministic local Responses stub emit that call. The frontend sends the request to a separate controller worker. That worker durably Prepare/Dispatches, commits one sink outcome, and is hard-killed before settlement; the supervisor restarts only the worker, which reopens its SQLite state, queries by stable key, settles without redispatch, and lets the still-live frontend answer the pending App Server request. The experiment does **not** claim that Codex 0.146.0 persists and replays an outstanding `item/tool/call` callback across App Server/frontend death; its callback map is in memory. Retain raw JSON-RPC, worker exit status, ledger, anchor, and sink evidence.
- Full completion rule: both commands exit zero; all 80 policy runs reach an explicit terminal/earliest-divergence status; every reached protected dispatch traverses `item/tool/call`; all raw events, process-exit sites, receipts, sink snapshots, durable heads, observation projections, and runtime hashes are retained; P3 satisfies every primary correctness metric; O0/O1 report the predeclared topology (C13/C14 before the same fresh Reserve), authority-lineage (C16/C18 before the same second Reserve), and effect-phase (C02/C04 before permission for the same physical `.attempt(e1,c1)`) ambiguity witnesses; O2 replays every fixed-suite edge with no mixed-label fiber. The previously proposed C02/C03 `FinalizeAbort` probe is retired because the current abstract `Settle` rule permits cancellation from `uncertain` and carries no authenticated-absence premise; it is not valid evidence for the existing LTS. Each JSON-RPC request times out after 15 seconds, a worker restart after 5 seconds, a turn after 30 seconds, and a case after 60 seconds; timeout is a retained terminal failure, never an implicit retry or hang.
- Raw-result path: `adapter/results/raw/`, `adapter/results/litmus.json`, `adapter/results/check.json`, and the current experiment directory for preflight/run/review logs.
- Checkpoint or recovery approach: each case receives isolated controller, anchor, and sink SQLite files. The supervisor keeps the App Server and JSON-RPC frontend alive, launches the controller worker as a child, injects a hard worker-process exit only at the named site, restarts that worker from the durable head, and never copies these stores into the simulated workspace checkpoint.

## Interpretation

- Positive result: all completion conditions hold. This supports the narrow claim that a dispatch-owning Codex client can instantiate the paper's refinement premises for one protected queryable sink and adapter-defined lifecycle operations.
- Negative or contradictory result: preserve the failing trace and name the failed premise. Duplicate outcome, bypass, wrong P3 decision, or unmapped edge rejects the tested adapter instantiation; it does not by itself refute the abstract authority-continuity invariant.
- Mixed or inconclusive result: if dynamic dispatch works but native lineage or adapter-defined topology cannot yield a noncircular mapping, report runtime correspondence only and keep concrete refinement unestablished. If only O2 replay fails, demote the observability extension and retain the enforcement result that remains independently valid. The absence of a P0 duplicate during worker-only crash is uninterpretable for full-client-loss safety because the live frontend and sink retain the same call ID; only P0's authority/topology decisions are used.
- Target paper figure or table: one compact C01--C20 policy outcome table plus a small refinement-boundary diagram showing native App Server events, durable adapter events, abstract labels, and the mock sink. No latency figure is promised in this RQ3 experiment.
