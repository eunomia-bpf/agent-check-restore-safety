\section{Agent History Edges and Security Boundary}
\label{sec:lifecycle}

\subsection{Typed Agent history edges}

An Agent runtime does more than reconstruct an earlier process image.  It may
retain several descendants, replace one continuation while another remains
live, or combine results from histories that were previously alternatives.
Tool-using agents make these transformations security-relevant because they
choose the execution graph online while invoking services whose state is
outside the reconstructed process.

Current Agent interfaces expose fragments of this lifecycle.  Codex documents
thread creation, resume, fork lineage, and event streams, while Claude
documents both resuming and forking saved sessions
~\cite{codexappserver,claudesessions}.  Filesystem-oriented Agent substrates
add isolated worktrees or sandbox checkpoints
~\cite{wang2026fork,wu2026crab}.  These mechanisms reconstruct state, but their
names do not determine the future contract: a fork may choose one alternative
or keep parallel work co-durable; a restore may replace the current
continuation or leave both versions live; and a merge may select one arm or
retain commitments from both.

We therefore model six typed edges: choice and parallel Fork, replacing and
live Restore, and select and join Merge.  Each edge carries complete per-arm
may and required contracts.  Its type determines whether the arm families are
combined by choice or joint durability; a pure Checkpoint records
reconstructable state and changes no future contract by itself.  The required
family is part of the edge's semantics: removing a required continuation is
not a safe implementation of the same edge.

The graph need not be known in advance.  Admission handles one proposed edge
against one durable receipt prefix and one installed controller epoch.
Structural certificates may compose while that prefix is unchanged; a newly
durable receipt, a controller replacement, or a changed co-liveness contract
creates a new decision.  The prototype recomputes each request and reports
reuse eligibility rather than consuming a previous seal.

\subsection{The serialized monitor as reference semantics}

The security reference point is a global serialized atomic commit monitor.
Let $D$ be its authenticated durable receipt prefix.  Before making a fresh
cell configuration $X$ durable, the monitor checks the lineage conditions in
$\mathsf{PrefixOK}(X)$ against $D$ and atomically advances the prefix only if
the check succeeds.  With complete mediation and atomic prefix advancement,
this monitor guarantees safety: every durable prefix remains in the authority
family.

For a typed edge $op$, applying that same check to every generated candidate
configuration gives
\[
  \mathsf{Admitted}_{op}
  =\{X\in\mathsf{Candidate}_{op}\mid\mathsf{PrefixOK}(X)\}.
\]
Thus $\mathsf{Admitted}_{op}$ is not a competing policy; it is the exact
counterfactual future of the serialized monitor for this edge and fixed
prefix.  The additional question is fidelity.  If
$\mathsf{Required}_{op}\nsubseteq\mathsf{Admitted}_{op}$, the monitor can keep
the run safe only by eventually denying behavior that the edge declared
mandatory, as in the live-Restore example in \cref{sec:introduction}.  No
pruning-only realization preserves that edge; it must be rejected or proposed
under a different contract, identity allocation, or authority grant.

When the required future survives, the monitor can be specialized into the
controller topology created by the Agent edge.  A manifest with access
relation $E$, local controller families $L$, and co-liveness family $\Gamma$
induces $\mathsf{RawPhysical}(E,L,\Gamma)$.  It is a valid compilation exactly
when
\begin{equation}
\label{eq:lifecycle-monitor-compilation}
  \mathsf{Required}_{op}
  \subseteq\mathsf{RawPhysical}(E,L,\Gamma)
  \subseteq\mathsf{Admitted}_{op}.
\end{equation}
The centralized monitor is the one-controller realization of this boundary;
other realizations distribute or restrict the same admitted future.  The
claim is therefore exact specialization, not a claim that distributed gates
provide stronger safety than serialization.

\subsection{Workspace-rollback boundary}

The security state used by this reference semantics is not one snapshot.
Reconstructable context, files, processes, and staged payloads may follow the
typed edge.  Immutable receipts and authority bindings remain append-only;
the declared future is derived from leaf contracts and cell lineage; the
controller epoch must implement that future; and remote reality is not
generally reversible.  Rolling back every local byte is therefore insufficient
for three reasons.  First, an
external effect may already have escaped the rollback domain.  A restored
workspace can erase evidence of a message or remote write without undoing it;
Claude's documented checkpoint boundary, for example, excludes Bash,
external, and most subagent changes~\cite{claudecheckpoint}.  Second, rolling
back the receipt ledger would revive authority already spent, so the ledger
must advance independently of reconstructable state.  Third, total rollback
implements the wrong Agent edge when live Restore and parallel Fork retain
both descendants or join Merge combines them.

Consequently, no larger workspace snapshot substitutes for admission.  At a
fixed prefix, the monitor's future is a downward-closed family of sets that may
become durable together, not a vector of per-effect flags.  The installed
controller topology is a separate object because the state preserving that
correlation may live behind tool gates, reference monitors, or remote
services.

\subsection{Identity and topology evidence}

Exact monitor compilation depends on two independent identity relations.
$q_{\mathrm{cell}}$ says which copied handles meet the same atomic redemption
state; $q_{\mathrm{ctrl}}$ says which gate uses share the authoritative
controller state that preserves a correlation.  Aliases may pass through
several controllers, and distinct cells may rely on one joint controller, so
neither relation determines the other.  A fixed-manifest two-by-two
construction shows that erasing either relation while retaining the other
conflates compilable and noncompilable worlds
(\cref{prop:identity-erasure}).

Co-liveness evidence is likewise semantic rather than merely scheduling
telemetry.  Let $\Gamma$ be the downward-closed family of controller sets that
may remain jointly capable of durable commitment during one epoch.  If
distinct controllers can locally select $a$, $b$, and $c$ under the policy
that permits every pair but forbids the triple, their product realizes the
triple even though every local choice and every pair is admitted.  Compiling
the reference monitor must coordinate those controllers, restrict their
co-liveness, or reject the topology; atomic redemption of each individual cell
does not preserve this higher-order cut.

\subsection{Runtime integration contract}

The compiler sits before an Agent runtime installs a Fork, Restore, or Merge
edge.  A trusted adapter supplies (1) the typed edge and complete per-arm
may/required contracts; (2) cell-alias and authority-lineage evidence; (3) the
authenticated append-only receipt frontier; and (4) controller access, local
families, identities, versions, and co-liveness evidence.  The compiler and
independent verifier return a monitor-compilation seal or a replayable
counterexample.  The seal is a structural judgment about the proposed edge
and manifest, not permission to execute a tool.

A runtime using a positive judgment must atomically bind installation to the
same edge version, receipt prefix, and controller epoch represented by the
verified request.  Receipt growth, controller replacement, or any change to
$E,L,\Gamma$ invalidates that scope and forces readmission.  This paper
specifies that integration contract; the prototype neither installs
controllers nor replaces the atomic commitment substrate.

Agent lifecycle events and pre-tool hooks are prospective adapter surfaces
~\cite{codexappserver,codexhooks,claudesessions,claudehooks}.  Their existence
does not prove complete mediation, true handle aliases, shared controller
state, or the completeness of a future contract.  A concrete integration must
authenticate those facts and establish
\[
  \mathsf{Required}_{op}\subseteq\mathsf{Actual}
  \subseteq\mathsf{RawPhysical}(E,L,\Gamma).
\]
Combined with \cref{eq:lifecycle-monitor-compilation}, these obligations give
the full refinement chain and transport the serialized monitor's safety
guarantee to actual Agent commitments without deleting required behavior.

\subsection{Adversary, trusted base, and goal}

The adversary controls model output, copied or restored history, tool
arguments, proposed handles, and stale reconstructable state.  It may request
any documented Agent history edge or retry after an ambiguous external
outcome.  The trusted base consists of the policy and authority issuer, the
edge adapter, the append-only receipt integrity root, the atomic commitment
substrate, and the controller instances mediating protected commitments.  The
adapter must truthfully report edge semantics, complete leaf contracts, both
identity relations, and the installed topology; these facts cannot be inferred
reliably from natural-language intent or a filesystem diff.

For one fixed authority family and durable prefix, the semantic goal is to
preserve the edge's required future inside the greatest candidate subfamily
accepted by the serialized monitor.  The deployment goal is to compile that
boundary into controller topology satisfying
\cref{eq:lifecycle-monitor-compilation}; under runtime refinement, all actual
behavior is safe and all required behavior remains realizable.

The result remains conditional on truthful evidence, atomic installation,
complete mediation, controller freshness, and atomic redemption.  It does not
establish prompt integrity, infer policy from Agent text, validate leases,
guarantee useful task completion, prevent issue-time disclosure, or provide
physical exactly-once execution at an external sink.  Ambiguous external
outcomes still require authenticated status, sink idempotency, or explicitly
authorized compensation.
