\section{A Procurement Edit, End to End}
% 一个采购编辑的端到端过程
\label{sec:lifecycle}

Consider a procurement Agent authorized to place one order.
% 考虑一个获授权只能下单一次的采购 Agent。
The Agent reserves the budget and saves checkpoint \(k\) before approval.
% Agent 预留预算，并在审批前保存检查点 \(k\)。
The approval then uses its one-use permission and leaves a completion record.
% 审批随后使用其一次性权限并留下完成记录。
The Agent next requests a Fork between suppliers \(L\) and \(R\).
% Agent 随后请求在供应商 \(L\) 和 \(R\) 之间执行 Fork。
The workflow allows two outcomes: order from \(L\) or order from \(R\).
% 工作流允许两种结果：向 \(L\) 下单或向 \(R\) 下单。
In either outcome, payment must precede shipment:
% 在任一结果中，付款都必须先于发货：
\begin{equation}
\label{eq:running-outcomes}
\begin{split}
 o_L&:\ x_L^p\prec x_L^s,\\
 o_R&:\ x_R^p\prec x_R^s ,
\end{split}
\end{equation}
where \(x_i^p\) and \(x_i^s\) are payment and shipment occurrences.
% 其中，\(x_i^p\) 和 \(x_i^s\) 分别是付款发生项和发货发生项。
An occurrence identifies one call position in the workflow.
% 发生项标识工作流中的一个调用位置。
An effect identity identifies the protected action and one-use permission behind that position; the formulas call it a cell \(d\).
% 效果标识指明该位置背后的受控动作和一次性权限；公式中将其称为单元 \(d\)。

The two shipment calls share one effect identity:
% 两个发货调用共享一个效果标识：
\[
 q_{\rm cell}(x_L^s)=q_{\rm cell}(x_R^s)=d_s.
\]
The two payment calls instead have different effect identities \(d_L^p\) and \(d_R^p\).
% 两个付款调用则具有不同的效果标识 \(d_L^p\) 和 \(d_R^p\)。
A later Restore of \(k\) creates a new approval occurrence \(x_a'\), but both approval occurrences refer to the same effect identity \(d_a\).
% 随后 Restore 到 \(k\) 会创建新的审批发生项 \(x_a'\)，但两个审批发生项都指向同一个效果标识 \(d_a\)。

The receipt log \(\Delta\) records newly authorized effects in order.
% 回执日志 \(\Delta\) 按顺序记录新获得授权的效果。
The notation \(\mathsf{lab}(\Delta)\) keeps only their permission labels.
% 记号 \(\mathsf{lab}(\Delta)\) 只保留这些效果的权限标签。
Budget reservation contributes \(r\), approval contributes \(a\), the two payments contribute \(p_L\) and \(p_R\), and shipment contributes \(s\).
% 预算预留贡献 \(r\)，审批贡献 \(a\)，两种付款分别贡献 \(p_L\) 和 \(p_R\)，发货贡献 \(s\)。
At the Fork request, \(\mathsf{lab}(\Delta)=ra\).
% 在 Fork 请求处，\(\mathsf{lab}(\Delta)=ra\)。
The policy allows prefixes of \(rap_Ls\) and \(rap_Rs\), but never both payments or a payment before approval.
% 策略允许 \(rap_Ls\) 和 \(rap_Rs\) 的前缀，但绝不允许两笔付款同时发生，也不允许付款先于审批。
Although the supplier outcomes are exclusive, both must still have a safe way to finish when the Fork is checked.
% 尽管两个供应商结果互斥，但在检查 Fork 时，二者都必须仍有安全完成方式。

\paragraph{How the checker handles the Fork}
% 检查器如何处理 Fork
The Agent submits only \(u=\mathsf{ForkChoice}(b,\sigma)\).
% Agent 只提交 \(u=\mathsf{ForkChoice}(b,\sigma)\)。
The trusted controller, not the Agent, constructs the edited workflow from the registered edit schema.
% 可信控制器而非 Agent 根据已注册编辑模式构造编辑后的工作流。
It reads the workflow, authenticated execution record, receipt log, ordered dispatch queue, and policy, written \((\kappa,H,\Delta,\mathsf{out},\mathcal A)\).
% 它读取工作流、经认证执行记录、回执日志、有序派发队列和策略，记为 \((\kappa,H,\Delta,\mathsf{out},\mathcal A)\)。
From these records it derives the edited workflow, its required outcomes, and the effect identity behind every call position.
% 控制器从这些记录中推导编辑后的工作流、要求实现的结果以及每个调用位置背后的效果标识。

Write \(M_o\) for the policy-safe completions of outcome \(o\).
% 以 \(M_o\) 表示结果 \(o\) 的策略安全完成路径。
In this example, each outcome has one allowed call order:
% 在本例中，每个结果都有一种允许的调用顺序：
\[
\begin{aligned}
 z_L&=\Fresh(x_L^p,d_L^p)\Fresh(x_L^s,d_s),\\
 z_R&=\Fresh(x_R^p,d_R^p)\Fresh(x_R^s,d_s).
\end{aligned}
\]
Thus \(M_{o_L}=\{z_L\}\), \(M_{o_R}=\{z_R\}\), and \(\widehat B^\dagger=\{(o_L,z_L),(o_R,z_R)\}\), with \(W^\dagger\) their prefix closure.
% 因此，\(M_{o_L}=\{z_L\}\)、\(M_{o_R}=\{z_R\}\)，且 \(\widehat B^\dagger=\{(o_L,z_L),(o_R,z_R)\}\)，其中 \(W^\dagger\) 是它们的前缀闭包。
The checker builds monitor \(\mathsf{Can}(W^\dagger,\pi_2\widehat B^\dagger)\), binds the answer to this source snapshot, and atomically installs the monitor and replacement authorization tokens under a new monitor version.
% 检查器构造监控器 \(\mathsf{Can}(W^\dagger,\pi_2\widehat B^\dagger)\)，将答案绑定到该源状态快照，并在新的监控器版本下原子安装监控器和替代授权令牌。
The installed monitor allows only these partial executions.
% 已安装监控器只允许这些部分执行。
For each protected call, \Fresh means that the effect identity receives its first receipt, while \Alias means that another call position reuses the existing receipt.
% 对每个受控调用，\Fresh 表示该效果标识获得第一条回执，而 \Alias 表示另一个调用位置复用已有回执。
If policy excludes \(rap_Rs\), then \(M_{o_R}=\varnothing\), and the Fork is rejected because pruning supplier \(R\) would change its meaning.
% 如果策略排除 \(rap_Rs\)，则 \(M_{o_R}=\varnothing\)，并且该 Fork 会被拒绝，因为剪除供应商 \(R\) 将改变其含义。
Rejection returns a ranked certificate explaining which completions were removed and why, rather than letting the Agent weaken the requested edit.
% 拒绝会返回一份带秩证书，解释哪些完成路径被删除以及删除原因，而不会让 Agent 弱化请求的编辑。
\Cref{sec:admission} gives a harder case where each outcome initially has a safe completion, but every possible implementation eventually reaches a partial execution after which some still-possible outcome cannot finish safely.
% \Cref{sec:admission} 给出一个更困难的情形：每个结果起初都有安全完成路径，但任何可能实现最终都会到达某段部分执行，此后某个仍可能的结果无法安全完成。

\paragraph{Adding new rules without changing current requirements}
% 在不改变当前要求的情况下增加新规则
A registered extension \(\mathsf{Extend}(\xi)\) can add compensation schemas and policy entries while the procurement execution remains active.
% 已注册扩展 \(\mathsf{Extend}(\xi)\) 可以在采购执行仍然活跃时增加补偿模式与策略条目。
The protected-call and policy authorities must both sign \(\xi\).
% 受控调用权限方与策略权限方都必须签署 \(\xi\)。
The extension preserves every current outcome, call position, effect identity, receipt, checkpoint, cursor, dispatch-queue entry, and causal edge.
% 该扩展保留每个当前结果、调用位置、效果标识、回执、检查点、游标、派发队列条目和因果边。
It only appends new schema and registry rows and enlarges the policy.
% 它只追加新的模式和注册表行，并扩大策略。
The controller then rebuilds the monitor and atomically changes its version.
% 控制器随后重新构造监控器并原子更改其版本。
A later edit may use the new schema, but the Agent cannot change an earlier call or remove a currently required outcome.
% 后续编辑可以使用新模式，但 Agent 无法改变先前调用或移除当前仍要求实现的结果。

A \emph{policy domain} is the set of protected actions governed by one policy, one receipt log, and one monitor that is replaced atomically.
% \emph{策略域}是由一个策略、一个回执日志和一个原子替换的监控器共同管理的一组受控动作。

\paragraph{The \Fresh race}
% \Fresh 竞态
After the shared approval and before either payment, the Agent requests \(\mathsf{MergeSelect}(g,L,\sigma)\).
% 在共享审批之后、任一付款之前，Agent 请求 \(\mathsf{MergeSelect}(g,L,\sigma)\)。
If the payment call \(x_R^p\) from the old supplier-\(R\) branch is authorized first, it selects \(R\) and changes \(\mathsf{lab}(\Delta)\) from \(ra\) to \(rap_R\).
% 如果旧供应商 \(R\) 分支的付款调用 \(x_R^p\) 先获得授权，它就会选择 \(R\)，并将 \(\mathsf{lab}(\Delta)\) 从 \(ra\) 改为 \(rap_R\)。
Selecting \(L\) must therefore be re-derived and rejected.
% 因此，选择 \(L\) 必须重新推导并被拒绝。
If the Merge installation occurs first, it closes the old monitor version and gives every current call a new authorization token before any later \(x_R^p\) can be authorized.
% 如果 Merge 先安装，它会关闭旧监控器版本，并在后续任何 \(x_R^p\) 获得授权之前为每个当前调用提供新的授权令牌。
Leaving the old monitor version active would allow both payments.
% 让旧监控器版本继续有效会允许两笔付款。

\paragraph{The \Alias race}
% \Alias 竞态
Now consider the live Restore in \cref{fig:two-histories}.
% 现在考虑 \cref{fig:two-histories} 中的活跃 Restore。
Copying checkpoint \(k\) creates a new approval occurrence \(x_a'\) with a new monitor entry and authorization token, but it retains effect identity \(d_a\).
% 复制检查点 \(k\) 会创建新的审批发生项 \(x_a'\) 以及新的监控器入口和授权令牌，但它保留效果标识 \(d_a\)。
Because \(d_a\) already has a receipt, executing \(x_a'\) is an \Alias: the restored branch advances past approval without creating another receipt.
% 由于 \(d_a\) 已有回执，执行 \(x_a'\) 是一次 \Alias：恢复后的分支越过审批，但不会创建另一条回执。
A concurrent join or replacement computed before that progress is stale even though the receipt log has not changed.
% 在该推进之前计算的并发 join 或替换已经过期，即使回执日志没有变化。
The installation check must therefore compare the ordered occurrence record \(\chi\) as well as the receipt log.
% 因此，安装检查除了比较回执日志外，还必须比较有序发生项记录 \(\chi\)。
For this \(\mathsf{RestoreLive}\) request, the checker either installs the derived monitor under a new version or returns a ranked rejection certificate.
% 对于该 \(\mathsf{RestoreLive}\) 请求，检查器要么在新版本下安装推导出的监控器，要么返回带秩拒绝证书。

The example exposes the whole problem.
% 这个例子揭示了完整的问题。
Workspace equality does not reveal which branches remain active, and receipt equality does not reveal \Alias progress.
% 工作区相等性无法揭示哪些分支仍然活跃，而回执相等性无法揭示 \Alias 推进。
Effect-identity equality alone does not reveal which outcomes the edit must preserve.
% 仅有效果标识相等性也无法揭示编辑必须保留哪些结果。
A replacement monitor proposed by the Agent cannot certify any of these facts.
% Agent 提出的替代监控器无法认证这些事实。
\Cref{sec:model} therefore derives the edited workflow from the registered schema and authenticated execution record.
% 因此，\Cref{sec:model} 从已注册模式和经认证执行记录中推导编辑后的工作流。
