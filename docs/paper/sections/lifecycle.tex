\section{Execution-Edit Safety}
% 执行编辑安全
\label{sec:lifecycle}

Consider an Agent operating an approval workflow with one authorized order.
% 考虑一个运行审批工作流且只获授权下单一次的 Agent。
The Agent reserves the budget and saves checkpoint \(k\) before approval.
% Agent 预留预算，并在审批前保存检查点 \(k\)。
The approval is then authorized once, creating an authorization record that Restore does not delete.
% 审批随后只获得一次授权，并创建一条 Restore 不会删除的授权记录。
The Agent next requests a Fork between suppliers \(L\) and \(R\).
% Agent 随后请求在供应商 \(L\) 和 \(R\) 之间执行 Fork。
The workflow allows two outcomes: order from \(L\) or order from \(R\).
% 工作流允许两种结果：向 \(L\) 下单或向 \(R\) 下单。
In either outcome, payment authorization must precede shipment authorization:
% 在任一结果中，付款授权都必须先于发货授权：
\begin{equation}
\label{eq:running-outcomes}
\begin{split}
 o_L&:\ x_L^p\prec x_L^s,\\
 o_R&:\ x_R^p\prec x_R^s ,
\end{split}
\end{equation}
where \(x_i^p\) and \(x_i^s\) are payment and shipment occurrences.
% 其中，\(x_i^p\) 和 \(x_i^s\) 分别是付款发生项和发货发生项。
An occurrence identifies one call position in the workflow.
% 发生项标识工作流中的一个调用位置。
An effect identity \(d\) identifies the protected action and one-use permission behind that position.
% 效果标识 \(d\) 指明该位置背后的受控动作和一次性权限。

The two shipment calls share one effect identity:
% 两个发货调用共享一个效果标识：
\[
 q_{\rm eff}(x_L^s)=q_{\rm eff}(x_R^s)=d_s.
\]
The two payment calls instead have different effect identities \(d_L^p\) and \(d_R^p\).
% 两个付款调用则具有不同的效果标识 \(d_L^p\) 和 \(d_R^p\)。

The authorization log \(\Delta\) records newly authorized effects in order.
% 授权日志 \(\Delta\) 按顺序记录新获得授权的效果。
The notation \(\mathsf{lab}(\Delta)\) keeps only their permission labels.
% 记号 \(\mathsf{lab}(\Delta)\) 只保留这些效果的权限标签。
Budget reservation contributes \(r\), approval contributes \(a\), the two payments contribute \(p_L\) and \(p_R\), and shipment contributes \(s\).
% 预算预留贡献 \(r\)，审批贡献 \(a\)，两种付款分别贡献 \(p_L\) 和 \(p_R\)，发货贡献 \(s\)。
At the Fork request, \(\mathsf{lab}(\Delta)=ra\).
% 在 Fork 请求处，\(\mathsf{lab}(\Delta)=ra\)。
The policy allows prefixes of \(rap_Ls\) and \(rap_Rs\), but never both payments or a payment before approval.
% 策略允许 \(rap_Ls\) 和 \(rap_Rs\) 的前缀，但绝不允许两笔付款都发生，也不允许付款先于审批。
Although the supplier outcomes are exclusive, both must still have a safe way to finish when the Fork is checked.
% 尽管两个供应商结果互斥，但在检查 Fork 时，二者都必须仍有安全完成方式。

\subsection{Accepted and Rejected Forks}
% 被接受与被拒绝的 Fork
The Agent submits only \(u=\mathsf{ForkChoice}(b,\sigma)\).
% Agent 只提交 \(u=\mathsf{ForkChoice}(b,\sigma)\)。
The trusted controller, not the Agent, constructs the edited workflow from the registered edit schema.
% 可信控制器而非 Agent 根据已注册编辑模式构造编辑后的工作流。
From the authenticated workflow, execution record, authorization log, and policy, it derives the edited workflow, its required outcomes, and the effect identity behind every call position.
% 控制器根据经认证的工作流、执行记录、授权日志与策略，推导编辑后的工作流、要求实现的结果以及每个调用位置背后的效果标识。

Write \(M_o\) for the policy-safe completions of outcome \(o\).
% 以 \(M_o\) 表示结果 \(o\) 的策略安全完成路径。
Each outcome has one allowed call order:
% 每个结果都有一种允许的调用顺序：
\[
\begin{aligned}
 z_L&=\Fresh(x_L^p,d_L^p)\Fresh(x_L^s,d_s),\\
 z_R&=\Fresh(x_R^p,d_R^p)\Fresh(x_R^s,d_s).
\end{aligned}
\]
Thus \(M_{o_L}=\{z_L\}\) and \(M_{o_R}=\{z_R\}\).
% 因此，\(M_{o_L}=\{z_L\}\) 且 \(M_{o_R}=\{z_R\}\)。
Each supplier outcome is preserved, and every permitted prefix can still finish safely.
% 每个供应商结果都得到保留，且每个获准前缀仍能安全完成。
The verdict is therefore \emph{Accept}: both supplier outcomes remain possible, every permitted prefix is policy safe, and each such prefix can still reach a complete outcome.
% 因而判定为\emph{接受}：两个供应商结果仍然可能，每个获准前缀都满足策略，且每个这样的前缀仍能到达完整结果。
If policy excludes \(rap_Rs\), then \(M_{o_R}=\varnothing\), and the Fork is rejected because pruning supplier \(R\) would change its meaning.
% 如果策略排除 \(rap_Rs\)，则 \(M_{o_R}=\varnothing\)，并且该 Fork 会被拒绝，因为剪除供应商 \(R\) 将改变其含义。
Rejection returns a ranked certificate explaining which completions were removed and why, rather than letting the Agent weaken the requested edit.
% 拒绝会返回一份带秩证书，解释哪些完成路径被删除以及删除原因，而不会让 Agent 弱化请求的编辑。
The verdict in this variant is \emph{Reject}: checking only the surviving \(L\) branch would silently weaken the requested Fork.
% 该变体的判定为\emph{拒绝}：只检查保留下来的 \(L\) 分支会悄然削弱所请求的 Fork。

\subsection{Prefix-Unsafe Outcomes}
% 前缀不安全的结果

The previous rejection is visible at the start because one outcome has no safe completion.
% 前述拒绝在起点即可看出，因为其中一个结果没有安全完成路径。
A harder failure occurs when every outcome is initially safe in isolation, but no single monitor can keep all of them completable.
% 更困难的失败情形是：每个结果单独看起初都安全，但不存在一个监控器能让它们始终均可完成。
Let \(X,Y,Z\) be single-call contracts with permission labels \(x,y,z\), respectively, and consider
% 令 \(X,Y,Z\) 分别为权限标签为 \(x,y,z\) 的单调用契约，并考虑
\[
  X\otimes(Y\oplus Z)
  \qquad\text{under}\qquad
  \mathcal A=\Pref\{yx,xz\}.
\]
The two outcomes have safe complete traces \(yx\) and \(xz\).
% 两个结果分别具有安全完整轨迹 \(yx\) 和 \(xz\)。
However, executing the shared \(x\) call first keeps the \(X\otimes Y\) outcome possible while leaving only the forbidden continuation \(xy\).
% 然而，若先执行共享的 \(x\) 调用，\(X\otimes Y\) 结果仍然可能，但只剩下被禁止的后续轨迹 \(xy\)。
A monitor that exposes \(x\) is therefore unsafe, while a monitor that removes \(x\) destroys the \(X\otimes Z\) outcome.
% 因而，暴露 \(x\) 的监控器不安全，而移除 \(x\) 的监控器又会破坏 \(X\otimes Z\) 结果。
The exact verdict is \emph{Reject}, even though an outcome-by-outcome check would accept.
% 精确判定为\emph{拒绝}，尽管逐结果检查会接受。
\Cref{sec:admission} formalizes this failure as a greatest-fixed-point elimination rather than assuming that one safe trace per outcome is enough.
% \Cref{sec:admission} 将这一失败形式化为最大不动点淘汰过程，而不是假设每个结果有一条安全轨迹就已足够。

\paragraph{\Fresh-authorization race}
% \Fresh 授权竞态
After the shared approval and before either payment, the Agent requests \(\mathsf{MergeSelect}(g,L,\sigma)\).
% 在共享审批之后、任一付款之前，Agent 请求 \(\mathsf{MergeSelect}(g,L,\sigma)\)。
If the payment call \(x_R^p\) from the old supplier-\(R\) branch is authorized first, it selects \(R\) and changes \(\mathsf{lab}(\Delta)\) from \(ra\) to \(rap_R\).
% 如果旧供应商 \(R\) 分支的付款调用 \(x_R^p\) 先获得授权，它就会选择 \(R\)，并将 \(\mathsf{lab}(\Delta)\) 从 \(ra\) 改为 \(rap_R\)。
Selecting \(L\) must therefore be re-derived and rejected.
% 因此，选择 \(L\) 必须重新推导并被拒绝。
If the Merge installation occurs first, it closes the old monitor version and gives every current call a new authorization token before any later \(x_R^p\) can be authorized.
% 如果 Merge 先安装，它会关闭旧监控器版本，并在后续任何 \(x_R^p\) 获得授权之前为每个当前调用提供新的授权令牌。
Leaving the old monitor version active would allow both payments.
% 让旧监控器版本继续有效会允许两笔付款。

\paragraph{Receipt-reuse race}
% 收据复用竞态
Now consider the Restore that keeps both continuations in \cref{fig:two-histories}.
% 现在考虑 \cref{fig:two-histories} 中保留两条延续的 Restore。
A later Restore of \(k\) creates a new approval occurrence \(x_a'\), but both approval occurrences refer to the same effect identity \(d_a\).
% 随后 Restore 到 \(k\) 会创建新的审批发生项 \(x_a'\)，但两个审批发生项都指向同一个效果标识 \(d_a\)。
The restored occurrence is a new workflow position but retains effect identity \(d_a\).
% 恢复出的发生项是一个新的工作流位置，但保留效果标识 \(d_a\)。
Because \(d_a\) already has an authorization record, executing \(x_a'\) is an \Alias: the restored branch advances past approval without creating another authorization record.
% 由于 \(d_a\) 已有授权记录，执行 \(x_a'\) 是一次 \Alias：恢复后的分支越过审批，但不会创建另一条授权记录。
A concurrent join or replacement computed before that progress is stale even though the authorization log has not changed.
% 在该推进之前计算的并发 join 或替换已经过期，即使授权日志没有变化。
The installation check must therefore compare the ordered occurrence record \(\chi\) as well as the authorization log.
% 因此，安装检查除了比较授权日志外，还必须比较有序发生项记录 \(\chi\)。
For this \(\mathsf{RestoreLive}\) request, the checker either installs the derived monitor under a new version or returns a ranked rejection certificate.
% 对于该 \(\mathsf{RestoreLive}\) 请求，检查器要么在新版本下安装推导出的监控器，要么返回带秩拒绝证书。

These executions determine the three requirements used throughout the paper.
% 这些执行确定全文采用的三项要求。
First, an edit must preserve every outcome that the authenticated source still requires.
% 第一，编辑必须保留经认证源状态仍要求实现的每个结果。
Second, after every permitted prefix, every outcome still compatible with that prefix must retain a safe completion.
% 第二，在每个获准前缀之后，每个仍与该前缀兼容的结果都必须保留一条安全完成路径。
Third, the derived monitor and its authorization tokens must be installed atomically against concurrent protected calls.
% 第三，派生监控器及其授权令牌必须相对于并发受控调用原子安装。
\Cref{sec:model} now defines the authenticated state and fixes this security objective before \cref{sec:admission} constructs the checker.
% \Cref{sec:model} 接下来定义认证状态并确定这一安全目标，随后 \cref{sec:admission} 再构造检查器。
