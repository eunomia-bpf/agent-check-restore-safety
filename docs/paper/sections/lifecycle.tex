\section{Execution-Edit Safety}
% 执行编辑安全
\label{sec:lifecycle}

Imagine an Agent buying one laptop for a school.
% 设想一个为学校购买一台笔记本电脑的 Agent。
It reserves the budget, saves checkpoint \(k\), receives one purchase approval, and then compares suppliers \(L\) and \(R\).
% 它预留预算、保存检查点 \(k\)、取得一次购买审批，然后比较供应商 \(L\) 和 \(R\)。
A careless Restore or Merge could request approval twice, pay both suppliers, or permit shipment before the selected supplier is paid.
% 欠考虑的 Restore 或 Merge 可能重复请求审批、同时向两个供应商付款，或在向选定供应商付款前就允许发货。
A safe execution approves the purchase once, pays exactly one supplier, and permits shipment only after that payment.
% 安全执行只批准一次购买，只向一个供应商付款，并且仅在付款后允许发货。

The resulting \emph{workflow} records which calls may occur, in what order, and which results count as completion.
% 由此得到的\emph{工作流}记录哪些调用可以发生、调用次序以及哪些结果算作完成。
In this example, it authorizes at most one purchase.
% 在本例中，它至多授权一次采购。
The Agent reserves the budget and saves checkpoint \(k\) before approval.
% Agent 预留预算，并在审批前保存检查点 \(k\)。
The approval is then authorized once, creating an authorization record that Restore does not delete.
% 审批随后只获得一次授权，并创建一条 Restore 不会删除的授权记录。
The Agent next requests a Fork between suppliers \(L\) and \(R\).
% Agent 随后请求在供应商 \(L\) 和 \(R\) 之间执行 Fork。
The workflow allows two results: order from \(L\) or order from \(R\).
% 工作流允许两种结果：向 \(L\) 下单或向 \(R\) 下单。
In either result, payment authorization must precede shipment authorization:
% 在任一结果中，付款授权都必须先于发货授权：
\begin{equation}
\label{eq:running-results}
\begin{split}
 o_L&:\ x_L^p\prec x_L^s,\\
 o_R&:\ x_R^p\prec x_R^s ,
\end{split}
\end{equation}
where \(x_i^p\) and \(x_i^s\) are payment and shipment calls.
% 其中，\(x_i^p\) 和 \(x_i^s\) 分别是付款调用和发货调用。
A \emph{workflow call} \(x\) is one place in this structure where the runtime can invoke a tool.
% \emph{工作流调用} \(x\) 是该结构中运行时可以调用工具的一个位置。
The function \(q_{\rm act}(x)=d\) records which tool action the call refers to.
% 函数 \(q_{\rm act}(x)=d\) 记录该调用指向哪个工具动作。
Calls that refer to the same action share one authorization record.
% 指向同一个动作的调用共享一条授权记录。

In this example, both shipment calls authorize the same one-order shipment:
% 在这个例子中，两个发货调用都授权同一笔订单的发货：
\[
 q_{\rm act}(x_L^s)=q_{\rm act}(x_R^s)=d_s.
\]
The two payment calls instead refer to different actions \(d_L^p\) and \(d_R^p\).
% 两个付款调用则指向不同的动作 \(d_L^p\) 和 \(d_R^p\)。

The authorization log \(\Delta\) records newly authorized actions in order.
% 授权日志 \(\Delta\) 按顺序记录新获得授权的动作。
The notation \(\mathsf{lab}(\Delta)\) keeps only their authorization labels.
% 记号 \(\mathsf{lab}(\Delta)\) 只保留这些动作的授权标签。
Budget reservation contributes \(r\), approval contributes \(a\), the two payments contribute \(p_L\) and \(p_R\), and shipment contributes \(s\).
% 预算预留贡献 \(r\)，审批贡献 \(a\)，两种付款分别贡献 \(p_L\) 和 \(p_R\)，发货贡献 \(s\)。
At the Fork request, \(\mathsf{lab}(\Delta)=ra\).
% 在 Fork 请求处，\(\mathsf{lab}(\Delta)=ra\)。
The policy allows every partial authorization sequence of \(rap_Ls\) and \(rap_Rs\), but never both payments or a payment before approval.
% 策略允许 \(rap_Ls\) 和 \(rap_Rs\) 的每段部分授权序列，但绝不允许两笔付款都发生，也不允许付款先于审批。
Although the supplier results are exclusive, both must still have a safe way to finish when the Fork is checked.
% 尽管两个供应商结果互斥，但在检查 Fork 时，二者都必须仍有安全完成方式。

\subsection{Accepted and Rejected Forks}
% 被接受与被拒绝的 Fork
The Agent sends \(u=\mathsf{ForkChoice}(b,\sigma)\), which names a current branch and a registered edit rule.
% Agent 发送 \(u=\mathsf{ForkChoice}(b,\sigma)\)，其中指明一个当前分支和一条已注册编辑规则。
Here, the rule identified by \(\sigma\) turns branch \(b\) into the exclusive supplier-\(L\) and supplier-\(R\) copies shown below.
% 在这里，\(\sigma\) 指明的规则把分支 \(b\) 变为下文所示的供应商 \(L\) 与供应商 \(R\) 互斥副本。
The trusted runtime constructs the edited workflow from the execution record.
% 可信运行时根据执行记录构造编辑后的工作流。
It also derives the results that remain required and the action referred to by every workflow call.
% 可信运行时还推导仍然要求实现的结果，以及每个工作流调用所指向的动作。

Write \(M_o\) for the ways to complete result \(o\) while obeying the policy.
% 以 \(M_o\) 表示遵守策略并完成结果 \(o\) 的方式。
Each result has one allowed call order:
% 每个结果都有一种允许的调用顺序：
\[
\begin{aligned}
 z_L&=\Fresh(x_L^p,d_L^p)\Fresh(x_L^s,d_s),\\
 z_R&=\Fresh(x_R^p,d_R^p)\Fresh(x_R^s,d_s).
\end{aligned}
\]
Thus \(M_{o_L}=\{z_L\}\) and \(M_{o_R}=\{z_R\}\).
% 因此，\(M_{o_L}=\{z_L\}\) 且 \(M_{o_R}=\{z_R\}\)。
These sequences contain the calls after the edit, while the existing log contributes the earlier authorization sequence \(ra\).
% 这些序列包含编辑后的调用，而现有日志提供先前的授权序列 \(ra\)。
The verdict is \(\mathsf{Accepted}\): both supplier results remain possible, the calls performed so far always obey policy, and each result can be completed.
% 判定为 \(\mathsf{Accepted}\)：两个供应商结果仍然可能，已经执行的调用始终满足策略，并且每个结果都能完成。
If policy excludes \(rap_Rs\), then \(M_{o_R}=\varnothing\), and the Fork is rejected because pruning supplier \(R\) would change its meaning.
% 如果策略排除 \(rap_Rs\)，则 \(M_{o_R}=\varnothing\)，并且该 Fork 会被拒绝，因为剪除供应商 \(R\) 将改变其含义。
Rejection returns a proof listing the order in which completions were removed and the reason for each removal, rather than letting the Agent weaken the requested edit.
% 拒绝会返回一份证明，列出完成路径的移除顺序及每次移除的原因，而不会让 Agent 弱化请求的编辑。
