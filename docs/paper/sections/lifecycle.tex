\section{Execution-Edit Safety}
% 执行编辑安全
\label{sec:lifecycle}

Imagine an Agent buying one laptop for a school.
% 设想一个为学校购买一台笔记本电脑的 Agent。
It reserves the budget, saves checkpoint \(k\), receives one purchase approval, and then compares suppliers \(L\) and \(R\).
% 它预留预算、保存检查点 \(k\)、取得一次购买审批，然后比较供应商 \(L\) 和 \(R\)。
A careless Restore or Merge could request approval twice, pay both suppliers, or permit shipment before the selected supplier is paid.
% 欠考虑的 Restore 或 Merge 可能重复请求审批、同时向两个供应商付款，或在向选定供应商付款前就允许发货。
A safe execution approves the purchase once, pays exactly one supplier, and permits shipment only after that payment.
% 安全执行只批准一次购买，只向一个供应商付款，并且仅在付款后允许发货。

We formalize this story as an approval workflow that authorizes at most one order.
% 我们把这个故事形式化为一个至多获授权下单一次的审批工作流。
The Agent reserves the budget and saves checkpoint \(k\) before approval.
% Agent 预留预算，并在审批前保存检查点 \(k\)。
The approval is then authorized once, creating an authorization record that Restore does not delete.
% 审批随后只获得一次授权，并创建一条 Restore 不会删除的授权记录。
The Agent next requests a Fork between suppliers \(L\) and \(R\).
% Agent 随后请求在供应商 \(L\) 和 \(R\) 之间执行 Fork。
The workflow allows two outcomes: order from \(L\) or order from \(R\).
% 工作流允许两种结果：向 \(L\) 下单或向 \(R\) 下单。
In either outcome, payment authorization must precede shipment authorization:
% 在任一结果中，付款授权都必须先于发货授权：
\begin{equation}
\label{eq:running-outcomes}
\begin{split}
 o_L&:\ x_L^p\prec x_L^s,\\
 o_R&:\ x_R^p\prec x_R^s ,
\end{split}
\end{equation}
where \(x_i^p\) and \(x_i^s\) are payment and shipment calls.
% 其中，\(x_i^p\) 和 \(x_i^s\) 分别是付款调用和发货调用。
A \emph{workflow call} \(x\) is one place where the workflow can invoke a protected tool.
% \emph{工作流调用} \(x\) 是工作流可以调用受控工具的一个位置。
The function \(q_{\rm act}(x)=d\) records which external action the call refers to.
% 函数 \(q_{\rm act}(x)=d\) 记录该调用指向哪个外部动作。
Calls that refer to the same action share one authorization record.
% 指向同一个动作的调用共享一条授权记录。

In this example, both shipment calls authorize the same one-order shipment:
% 在这个例子中，两个发货调用都授权同一笔订单的发货：
\[
 q_{\rm act}(x_L^s)=q_{\rm act}(x_R^s)=d_s.
\]
The two payment calls instead refer to different actions \(d_L^p\) and \(d_R^p\).
% 两个付款调用则指向不同的动作 \(d_L^p\) 和 \(d_R^p\)。

The authorization log \(\Delta\) records newly authorized actions in order.
% 授权日志 \(\Delta\) 按顺序记录新获得授权的动作。
The notation \(\mathsf{lab}(\Delta)\) keeps only their authorization labels.
% 记号 \(\mathsf{lab}(\Delta)\) 只保留这些动作的授权标签。
Budget reservation contributes \(r\), approval contributes \(a\), the two payments contribute \(p_L\) and \(p_R\), and shipment contributes \(s\).
% 预算预留贡献 \(r\)，审批贡献 \(a\)，两种付款分别贡献 \(p_L\) 和 \(p_R\)，发货贡献 \(s\)。
At the Fork request, \(\mathsf{lab}(\Delta)=ra\).
% 在 Fork 请求处，\(\mathsf{lab}(\Delta)=ra\)。
The policy allows prefixes of \(rap_Ls\) and \(rap_Rs\), but never both payments or a payment before approval.
% 策略允许 \(rap_Ls\) 和 \(rap_Rs\) 的前缀，但绝不允许两笔付款都发生，也不允许付款先于审批。
Although the supplier outcomes are exclusive, both must still have a safe way to finish when the Fork is checked.
% 尽管两个供应商结果互斥，但在检查 Fork 时，二者都必须仍有安全完成方式。

\subsection{Accepted and Rejected Forks}
% 被接受与被拒绝的 Fork
The Agent sends \(u=\mathsf{ForkChoice}(b,\sigma)\), which names a current branch and a registered edit rule.
% Agent 发送 \(u=\mathsf{ForkChoice}(b,\sigma)\)，其中指明一个当前分支和一条已注册编辑规则。
The trusted controller constructs the edited workflow from the execution record.
% 可信控制器根据执行记录构造编辑后的工作流。
It also derives the outcomes that remain required and the action referred to by every workflow call.
% 控制器还推导仍然要求实现的结果，以及每个工作流调用所指向的动作。

Write \(M_o\) for the ways to complete outcome \(o\) while obeying the policy.
% 以 \(M_o\) 表示遵守策略并完成结果 \(o\) 的方式。
Each outcome has one allowed call order:
% 每个结果都有一种允许的调用顺序：
\[
\begin{aligned}
 z_L&=\Fresh(x_L^p,d_L^p)\Fresh(x_L^s,d_s),\\
 z_R&=\Fresh(x_R^p,d_R^p)\Fresh(x_R^s,d_s).
\end{aligned}
\]
Thus \(M_{o_L}=\{z_L\}\) and \(M_{o_R}=\{z_R\}\).
% 因此，\(M_{o_L}=\{z_L\}\) 且 \(M_{o_R}=\{z_R\}\)。
These sequences contain the calls after the edit, while the existing log contributes the earlier prefix \(ra\).
% 这些序列包含编辑后的调用，而现有日志提供先前的前缀 \(ra\)。
Each supplier outcome is preserved, and every permitted prefix can still finish safely.
% 每个供应商结果都得到保留，且每个获准前缀仍能安全完成。
The verdict is therefore \emph{Accept} because both supplier outcomes remain possible, every permitted prefix is policy safe, and each such prefix can still reach a complete outcome.
% 因而判定为\emph{接受}，因为两个供应商结果仍然可能，每个获准前缀都满足策略，且每个这样的前缀仍能到达完整结果。
If policy excludes \(rap_Rs\), then \(M_{o_R}=\varnothing\), and the Fork is rejected because pruning supplier \(R\) would change its meaning.
% 如果策略排除 \(rap_Rs\)，则 \(M_{o_R}=\varnothing\)，并且该 Fork 会被拒绝，因为剪除供应商 \(R\) 将改变其含义。
Rejection returns a certificate listing the order in which completions were removed and the reason for each removal, rather than letting the Agent weaken the requested edit.
% 拒绝会返回一份证书，列出完成路径的移除顺序及每次移除的原因，而不会让 Agent 弱化请求的编辑。
The verdict in this variant is \emph{Reject} because checking only the surviving \(L\) branch would silently weaken the requested Fork.
% 该变体的判定为\emph{拒绝}，因为只检查保留下来的 \(L\) 分支会悄然削弱所请求的 Fork。

\subsection{Why Safe Endpoints Are Not Enough}
% 为什么安全终点仍然不够

The previous rejection is visible at the start because one outcome has no safe completion.
% 前述拒绝在起点即可看出，因为其中一个结果没有安全完成路径。
A harder failure occurs when every outcome is initially safe in isolation, but no single monitor can keep all of them completable.
% 更困难的失败情形是：每个结果单独看起初都安全，但不存在一个监控器能让它们始终均可完成。
Let \(X,Y,Z\) be single-call contracts with authorization labels \(x,y,z\), respectively, and consider
% 令 \(X,Y,Z\) 分别为授权标签为 \(x,y,z\) 的单调用契约，并考虑
\[
  X\otimes(Y\oplus Z)
  \qquad\text{under}\qquad
  \mathcal A=\Pref\{yx,xz\}.
\]
The two outcomes have safe complete traces \(yx\) and \(xz\).
% 两个结果分别具有安全完整轨迹 \(yx\) 和 \(xz\)。
However, executing the shared \(x\) call first keeps the \(X\otimes Y\) outcome possible while leaving only the forbidden continuation \(xy\).
% 然而，若先执行共享的 \(x\) 调用，\(X\otimes Y\) 结果仍然可能，但只剩下被禁止的后续轨迹 \(xy\)。
A monitor that allows \(x\) is therefore unsafe, while a monitor that forbids \(x\) destroys the \(X\otimes Z\) outcome.
% 因而，允许 \(x\) 的监控器不安全，而禁止 \(x\) 的监控器又会破坏 \(X\otimes Z\) 结果。
The exact verdict is \emph{Reject}, even though an outcome-by-outcome check would accept.
% 精确判定为\emph{拒绝}，尽管逐结果检查会接受。
\Cref{sec:admission} detects this failure by repeatedly removing executions that create such a bad prefix.
% \Cref{sec:admission} 通过反复移除会产生此类危险前缀的执行来检测这一失败。

\paragraph{New authorization during installation}
% 安装期间的新授权
After the shared approval and before either payment, the Agent requests \(\mathsf{MergeSelect}(g,L,\sigma)\).
% 在共享审批之后、任一付款之前，Agent 请求 \(\mathsf{MergeSelect}(g,L,\sigma)\)。
If the payment call \(x_R^p\) from the old supplier-\(R\) branch is authorized first, it selects \(R\) and changes \(\mathsf{lab}(\Delta)\) from \(ra\) to \(rap_R\).
% 如果旧供应商 \(R\) 分支的付款调用 \(x_R^p\) 先获得授权，它就会选择 \(R\)，并将 \(\mathsf{lab}(\Delta)\) 从 \(ra\) 改为 \(rap_R\)。
The controller must therefore check the Merge again and reject it.
% 因此，控制器必须重新检查该 Merge 并拒绝它。
If the Merge installation occurs first, it closes the old monitor version and gives every current call a new authorization token before any later \(x_R^p\) can be authorized.
% 如果 Merge 先安装，它会关闭旧监控器版本，并在后续任何 \(x_R^p\) 获得授权之前为每个当前调用提供新的授权令牌。
Leaving the old monitor version active would allow both payments.
% 让旧监控器版本继续有效会允许两笔付款。

\paragraph{Authorization reuse during installation}
% 安装期间的授权复用
Now consider the Restore that keeps both branches in \cref{fig:two-histories}.
% 现在考虑 \cref{fig:two-histories} 中保留两个分支的 Restore。
A later Restore of \(k\) creates a new approval call \(x_a'\), but both approval calls refer to the same action \(d_a\).
% 随后 Restore 到 \(k\) 会创建新的审批调用 \(x_a'\)，但两个审批调用都指向同一个动作 \(d_a\)。
The restored call is new, while the underlying action remains \(d_a\).
% 恢复出的调用是新的，而底层动作仍是 \(d_a\)。
Because \(d_a\) already has an authorization record, executing \(x_a'\) reuses that record.
% 由于 \(d_a\) 已有授权记录，执行 \(x_a'\) 会复用该记录。
The restored branch therefore advances past approval without creating another authorization record.
% 因此，恢复后的分支越过审批，而不会创建另一条授权记录。
A concurrent Merge or Restore result computed before that progress is now out of date even though the authorization log has not changed.
% 即使授权日志没有变化，在该进展之前计算的并发 Merge 或 Restore 结果也已经过期。
The installation check must therefore compare both the authorization log and the ordered record \(\chi\) of executed workflow calls.
% 因此，安装检查必须同时比较授权日志和记录已执行工作流调用顺序的 \(\chi\)。
For this \(\mathsf{RestoreLive}\) request, the checker either installs the derived monitor under a new version or returns a rejection certificate.
% 对于该 \(\mathsf{RestoreLive}\) 请求，检查器要么在新版本下安装推导出的监控器，要么返回拒绝证书。

Together, these executions give the paper's end-to-end safety rule.
% 这些执行共同给出本文的端到端安全规则。
An edit satisfies this rule when (1) it preserves every outcome still required by the execution record, (2) every allowed step obeys policy and can still reach a complete execution, (3) every required outcome that remains possible after those steps still has a safe way to finish, and (4) the resulting monitor and authorization tokens take effect atomically with concurrent calls.
% 当一次编辑满足以下条件时，它符合该规则：(1) 保留执行记录仍要求实现的每个结果；(2) 每个获准步骤都遵守策略且仍能到达完整执行；(3) 每个在这些步骤之后仍然可能实现的要求结果都保留安全完成方式；(4) 所得监控器与授权令牌相对于并发调用原子生效。
\Cref{sec:model} states this rule precisely, and \cref{sec:admission} constructs the exact checker.
% \Cref{sec:model} 精确定义这一规则，\cref{sec:admission} 则构造精确检查器。
