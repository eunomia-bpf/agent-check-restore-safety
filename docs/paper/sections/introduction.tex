\section{Introduction}
% 引言
\label{sec:introduction}

Tool-using Agent runtimes can change an execution while it is in progress.
% 使用工具的 Agent 运行时可以在执行过程中改变后续执行。
They let an Agent Checkpoint an execution, Fork it into alternatives, Restore an earlier checkpoint, and Merge branches~\cite{codexappserver,claudesessions,claudecheckpoint,wang2026fork,wu2026crab,zhang2026agentlibos}.
% 它们允许 Agent Checkpoint 一次执行、将其 Fork 为多个备选方案、Restore 到较早的检查点，并 Merge 多个分支~\cite{codexappserver,claudesessions,claudecheckpoint,wang2026fork,wu2026crab,zhang2026agentlibos}。
These operations support exploration, recovery, and reuse without restarting the task.
% 这些操作支持探索、恢复与复用，而无需重新开始任务。
We call Fork, Restore, and Merge \emph{execution edits} because they change what the Agent will do next; Checkpoint records the current execution for a later edit.
% 我们把 Fork、Restore 和 Merge 称为\emph{执行编辑}，因为它们会改变 Agent 接下来做什么；Checkpoint 则记录当前执行，供后续编辑使用。

Consider an Agent buying one laptop for a school.
% 考虑一个为学校购买一台笔记本电脑的 Agent。
Before asking the school to approve the purchase, it saves checkpoint \(k\).
% 在请求学校批准购买之前，它保存检查点 \(k\)。
The school approves one purchase, and the Agent later chooses supplier \(R\) and authorizes payment.
% 学校批准一次购买，随后 Agent 选择供应商 \(R\) 并授权付款。
The Agent then restores \(k\) to compare supplier \(L\) and merges the \(L\) branch into the current execution.
% 随后 Agent Restore 到 \(k\) 以比较供应商 \(L\)，并把 \(L\) 分支 Merge 到当前执行中。
If the runtime sees only the restored workspace, it may request the same approval again or continue with \(L\) even though payment to \(R\) is already authorized~\cite{zheng2026acrfence}.
% 如果运行时只看到恢复后的工作区，它可能再次请求同一审批，或在已经授权向 \(R\) 付款后继续选择 \(L\)~\cite{zheng2026acrfence}。
Either result breaks the school's purchasing rules because the first repeats a one-time approval and the second combines incompatible supplier actions.
% 两种结果都会违反学校的采购规则，因为前者重复一次性审批，后者组合彼此不相容的供应商动作。

This example shows that the runtime cannot rely on the Agent's account of the execution.
% 这个例子说明，运行时不能依赖 Agent 对执行情况的描述。
The Agent may request an edit that omits an earlier action or an result the task still requires.
% Agent 可能请求一次编辑，而该编辑省略先前的动作或任务仍要求实现的结果。
The trusted runtime instead determines what may happen next from an \emph{execution record} that the Agent cannot modify; in this example, the record remembers the one-time approval and the authorized payment to \(R\).
% 可信运行时改为根据 Agent 无法修改的\emph{执行记录}确定后续可以发生什么；在本例中，该记录记住一次性审批和已经授权的 \(R\) 付款。
A \emph{tool action} is a policy-governed tool effect, such as that approval, payment, or shipment, and the runtime checks every such action against policy.
% \emph{工具动作}是由策略管理的工具效果，例如该审批、付款或发货；运行时依据策略检查每个此类动作。
Our security goal is therefore to prevent an edit from authorizing a tool action forbidden by policy or discarding an result that the task still requires.
% 因此，我们的安全目标是防止编辑授权策略禁止的工具动作，或丢弃任务仍要求实现的结果。
Meeting this goal requires four facts: (1) the task structure and its required results, (2) which calls refer to the same action, (3) earlier authorizations and call progress, and (4) which rules govern a call that overlaps the edit.
% 实现这一目标需要四类事实：(1) 任务结构及其要求实现的结果，(2) 哪些调用指向同一个动作，(3) 先前的授权与调用进展，以及 (4) 哪组规则管理与编辑重叠的调用。
Each fact can change the correct answer.
% 每类事实都可能改变正确答案。
The restored workspace, an execution trace alone, an authorization log alone, and the Agent's own description each omit information the checker may need.
% 恢复后的工作区、单独的执行轨迹、单独的授权日志以及 Agent 自己的描述，都各自缺少检查器可能需要的信息。

Existing approaches cover parts of this problem but do not derive its complete safety condition.
% 现有方法覆盖了该问题的部分环节，却没有推导其完整安全条件。
Agent systems provide branching, staged effects, transactions, or recovery checks~\cite{yu2026shepherd,li2025agentgit,langchain2026timetravel,patil2024goex,chang2025sagallm,mohammadi2026atomix,chen2026cordon,yang2026dart}.
% Agent 系统提供分支、分阶段效果、事务或恢复检查~\cite{yu2026shepherd,li2025agentgit,langchain2026timetravel,patil2024goex,chang2025sagallm,mohammadi2026atomix,chen2026cordon,yang2026dart}。
Control and synthesis choose behavior after a model of possible executions and desired final states has been supplied~\cite{dequeiroz2005multitasking,malik2008generalised,finkbeiner2022live,aceto2018suppressions}.
% 控制与综合方法则在可能执行及期望最终状态的模型已经给定后选择行为~\cite{dequeiroz2005multitasking,malik2008generalised,finkbeiner2022live,aceto2018suppressions}。
Neither line of work derives from a recorded execution everything that a particular edit must preserve before it takes effect.
% 这两类工作都不会从已有执行记录中推导出某次具体编辑在生效前必须保留的全部内容。

Our key idea is that an execution edit must preserve both past actions and results that are still required.
% 我们的关键思想是：执行编辑必须同时保留过去的动作和仍然要求实现的结果。
Every result required before the edit must remain required, already be satisfied by the recorded execution, or be explicitly removed by the same authority that required it.
% 编辑前要求实现的每个结果都必须继续作为要求、已经由所记录的执行满足，或由提出该要求的同一权限方明确移除。
The Agent requests an edit under a registered edit rule.
% Agent 根据一条已注册编辑规则请求编辑。
The trusted runtime checks the recorded task structure and determines from that record, rather than from Agent text, what may happen next and which requirements carry over.
% 可信运行时检查已记录的任务结构，并根据该记录而非 Agent 文本确定后续可以发生什么以及哪些要求继续有效。
The Agent therefore cannot obtain a favorable answer by describing an execution that omits earlier actions or required results.
% 因此，Agent 无法通过描述一个省略先前动作或要求结果的执行来获得有利答案。

This idea creates three technical problems.
% 这一思想带来三个技术问题。
First, calls copied by Fork or Restore may refer to the same underlying action, so the runtime must distinguish a new authorization from reuse of an earlier authorization and return value.
% 第一，由 Fork 或 Restore 复制的调用可能指向同一个底层动作，因此运行时必须区分新授权与对先前授权及返回值的复用。
Second, after every allowed partial execution, every result that is still required and still possible must retain a safe way to finish.
% 第二，在每段允许的部分执行之后，每个仍被要求且仍有可能实现的结果都必须保留安全完成方式。
The checker must enforce this condition without forbidding additional safe behavior.
% 检查器必须执行这一条件，同时不能额外禁止安全行为。
Third, the answer must take effect atomically with calls that overlap the edit and remain valid if the runtime or machine stops unexpectedly and later recovers.
% 第三，该答案必须与重叠编辑的调用原子排序，并在运行时或机器意外停止后恢复时继续有效。

We give an exact checker that either computes every safe way for a requested operation to proceed or proves that every possible implementation is unsafe.
% 我们给出一个精确检查器，它要么计算所请求操作安全推进的全部方式，要么证明每种可能实现都不安全。
For a requested edit, the runtime uses the current execution record to construct every allowed complete execution.
% 对于一次编辑请求，运行时使用当前执行记录构造所有允许的完整执行。
It removes an execution whenever one of its partial executions would leave a still-required result with no safe completion.
% 如果某个完整执行的部分执行会让仍然要求实现的结果失去安全完成方式，检查器就删除该完整执行。
If no execution remains, the runtime returns an independently checkable proof that no safe implementation exists.
% 如果没有完整执行留下，运行时返回一份可独立检查的证明，说明不存在安全实现。
Otherwise, the remaining executions contain every safe way for the edit to proceed.
% 否则，剩余执行包含该编辑安全推进的全部方式。
Before the edit takes effect, the runtime checks the current execution record again and atomically switches to the newly computed rules.
% 编辑生效之前，运行时再次检查当前执行记录，并原子切换到新计算出的规则。
Every overlapping call is therefore checked entirely under either the old rules or the new rules.
% 因此，每个重叠调用都完全依据旧规则或新规则进行检查。
\Cref{fig:two-histories} illustrates this process for an approval task containing Fork, Merge, Restore, and calls that overlap the atomic rule update.
% \Cref{fig:two-histories} 用一个包含 Fork、Merge、Restore 以及与原子规则更新重叠调用的审批任务展示这一过程。
\Cref{sec:lifecycle} derives the example step by step.
% \Cref{sec:lifecycle} 对该例逐步进行推导。
After Restore, the repeated approval call reuses the earlier authorization record instead of authorizing the approval again.
% Restore 之后，重复的审批调用复用先前的授权记录，而不会再次授权该审批。

\paragraph{Contributions}
% 贡献
\begin{enumerate}[leftmargin=*,itemsep=2pt,topsep=2pt]
\item \textbf{Safety model.}
% \textbf{安全模型。}
We define safety for Agent Checkpoint, Fork, Restore, and Merge from the execution record rather than letting the Agent choose what the edited execution contains.
% 我们根据执行记录定义 Agent Checkpoint、Fork、Restore 和 Merge 的安全性，而不是让 Agent 决定编辑后的执行包含什么。
The model preserves past actions and every still-required result, and it proves that any exact checker must distinguish answer-changing cases from each of the four record parts identified above.
% 该模型保留过去的动作和每个仍要求实现的结果，并证明任何精确检查器都必须区分上述四个记录部分中会改变答案的情形。

\item \textbf{Exact checking and runtime implementation.}
% \textbf{精确检查与运行时实现。}
We construct an executable checker that returns either every safe way for the edit to proceed or a proof that none exists.
% 我们构造一个可执行检查器，它返回该编辑安全推进的全部方式，或者返回不存在安全方式的证明。
Checkpoint has an exact check, and the checker accepts each of the six forms of Fork, Restore, and Merge exactly when a safe runtime implementation exists.
% Checkpoint 具有精确检查，而对于 Fork、Restore 和 Merge 的六种形式，当且仅当存在安全运行时实现时，检查器才接受。
The runtime puts the result into effect atomically, preserves safety across repeated edits and restarts, and has the same Agent-visible behavior as an ideal atomic machine.
% 运行时使判定结果原子生效，在重复编辑与重新启动过程中保持安全，并与理想原子机器具有相同的 Agent 可见行为。

\item \textbf{Mechanization and executable validation.}
% \textbf{机械化与可执行验证。}
Six Lean modules mechanize registration, all six edit forms, the atomic rule update, calls concurrent with that update, and preservation across finite executions.
% 六个 Lean 模块机械化注册、全部六种编辑形式、原子规则更新、与该更新并发的调用以及有限执行上的安全保持。
Nineteen paper-specific tests and measurements over 2--128 results exercise the executable checker.
% 十九项论文专用测试与覆盖 2--128 个结果的测量检验可执行检查器。
\end{enumerate}
