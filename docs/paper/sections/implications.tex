\section{Implications of Execution-Edit Safety}
% 执行编辑安全的含义
\label{sec:implications}

This section gives five consequences of the security condition.
% 本节说明该安全条件的五个直接结论。
Together, they explain why the runtime cannot decide an execution edit from only the target workflow or authorization log.
% 这些结论共同说明：运行时不能只根据目标工作流或授权日志判定一次执行编辑。

\paragraph{A smaller target can be unsafe}
% 更小的目标也可能不安全。
In the laptop example, suppose the Agent proposes keeping only supplier \(L\).
% 在笔记本电脑例子中，假设 Agent 提议只保留供应商 \(L\)。
Every remaining call may obey policy, but the edit removes the supplier-\(R\) result that the school still requires.
% 剩余的每个调用都可能遵守策略，但该编辑删除了学校仍然要求保留的供应商 \(R\) 结果。
The runtime may remove that result only if the execution record shows that it has already been satisfied or that the authority that required it has authorized its removal.
% 只有当执行记录表明该结果已经满足，或提出该要求的权限方已经授权移除时，运行时才能删除它。
Policy compliance of the remaining calls is therefore insufficient.
% 因而，只检查剩余调用是否遵守策略并不充分。

\paragraph{Complete plans can conflict}
% 完整计划可能相互冲突。
Consider two results over three registered calls \(x,y,z\), represented by \(X\otimes(Y\oplus Z)\).
% 考虑由 \(X\otimes(Y\oplus Z)\) 表示的两个结果，其中包含三个已注册调用 \(x,y,z\)。
Both results use \(x\); the first also uses \(y\), while the second also uses \(z\).
% 两个结果都使用 \(x\)；第一个结果还使用 \(y\)，第二个结果还使用 \(z\)。
One result can complete in the allowed order \(yx\), and the other can complete in the allowed order \(xz\), under
% 在下列策略下，一个结果可以按获准次序 \(yx\) 完成，另一个可以按获准次序 \(xz\) 完成：
\[
  \mathcal A=\{\epsilon,x,y,xz,yx\}.
\]
Checking the two results separately would therefore accept both.
% 因此，分别检查两个结果会接受二者。
The edit requires both results to remain available, so the runtime cannot silently implement only one.
% 该编辑要求两个结果都保持可用，因此运行时不能悄悄地只实施其中一个。
However, allowing \(x\) first leaves the first result with only the forbidden order \(xy\).
% 但是，先允许 \(x\) 会使第一个结果只剩下被禁止的次序 \(xy\)。
Refusing to allow \(x\) removes the second result's only permitted way to begin.
% 拒绝允许 \(x\) 又会删除第二个结果唯一获准的开始方式。
Thus any one set of runtime rules either strands the first result or suppresses the second, so the exact verdict is \(\mathsf{Reject}\).
% 因而，任何一组运行时规则都会使第一个结果无法完成或压制第二个结果，所以精确判定是 \(\mathsf{Reject}\)。

\paragraph{The authorization log can stay unchanged}
% 授权日志可能保持不变。
In \cref{fig:two-histories}, Restore creates a new workflow call \(x_a'\) that refers to the already authorized tool action \(d_a\).
% 在 \cref{fig:two-histories} 中，Restore 创建新的工作流调用 \(x_a'\)，但它指向已经授权的工具动作 \(d_a\)。
Processing \(x_a'\) reuses the existing authorization record, so the authorization log does not change, but the restored branch advances.
% 处理 \(x_a'\) 会复用已有授权记录，因此授权日志不变，但恢复后的分支取得了进展。
That progress can invalidate a Merge or Restore decision computed just before the reuse.
% 该进展会使复用之前刚计算出的 Merge 或 Restore 判定失效。
The execution record must therefore version every processed workflow call, including reuse.
% 因此，执行记录必须为每个已处理工作流调用记录版本，包括授权复用调用。
It must also preserve the mapping from workflow calls to tool actions: a restored call for the same purchase reuses an authorization record, whereas a call for a different purchase requires a new one.
% 执行记录还必须保留工作流调用到工具动作的映射：针对同一次采购的恢复调用复用授权记录，而针对另一笔采购的调用需要新的授权记录。
\Cref{thm:necessary-state} shows that changing only one of these recorded facts can change the correct answer.
% \Cref{thm:necessary-state} 表明，仅改变其中一项记录事实就可能改变正确答案。

\paragraph{New rules must use the checked record}
% 新规则生效时必须使用接受检查的记录。
Before new rules take effect, the runtime compares the current execution record with the version used by the checker.
% 新规则生效之前，运行时会把当前执行记录与检查器使用的版本进行比较。
If an old workflow call commits first, the runtime discards the candidate edit and checks it again.
% 如果旧工作流调用先提交，运行时会丢弃候选编辑并重新检查。
If the edit commits first, the old rule version and authorization tokens stop working.
% 如果编辑先提交，旧规则版本与授权令牌就会失效。
This ordering prevents an execution from combining old and new rules.
% 这一顺序防止一次执行混合使用新旧规则。

\paragraph{Acceptance and rejection have exact meanings}
% 接受与拒绝具有精确含义。
Rejection means that no runtime rules can safely implement the requested workflow under the same policy and required results.
% 拒绝意味着：在相同策略和要求结果下，不存在能够安全实施所请求工作流的运行时规则。
Changing that answer requires changing the edit, policy, or requirements.
% 要改变该答案，就必须改变编辑、策略或要求。
Acceptance returns the largest set of executions that the runtime may allow.
% 接受则返回运行时可以允许的最大执行集合。
After any allowed workflow calls, checking the remaining workflow again yields exactly the behavior left by the original check.
% 在执行任意获准的工作流调用之后，再次检查剩余工作流都会得到原检查留下的相同行为。
The runtime invariant separately preserves the same safety condition across later edits, rule updates, stops, and restarts.
% 运行时不变量还会在后续编辑、规则更新、停止与重启之间保持同一安全条件。

\Cref{sec:model} states the execution state and security objective precisely, \cref{sec:exact-check} constructs the exact checker, and \cref{sec:enforcement,sec:results} connect its verdict to atomic enforcement and the formal guarantees.
% \Cref{sec:model} 精确定义执行状态与安全目标，\cref{sec:exact-check} 构造精确检查器，\cref{sec:enforcement,sec:results} 则把检查判定与原子强制执行及形式保证连接起来。
